# 架构与核心业务规则

## 1. 架构边界

- **模块化单体优先。** 当前应用围绕一个 TypeScript 工作区，包括 `apps/web` 和 `apps/api`；业务模块共享领域对象、权限、审计和 PostgreSQL。只有经过容量与隔离需求验证后，才考虑抽离服务。
- **数据库：** PostgreSQL 16+；当前候选使用 Prisma 7.10.1 与显式 `@prisma/adapter-pg`。数据库连接配置由 `apps/api/prisma.config.ts` 读取。
- **后台任务：** `BackgroundJob` 持久化队列，任务必须具备幂等键、版本化 payload、有限重试与明确终态。无需先引入 Redis/Kafka/RabbitMQ 才能扩展业务模块。
- **AI：** LangGraph.js 运行时封装在 `apps/api/src/assistant/runtime/`，业务数据读取通过墨衡自己的只读服务；checkpoint 使用专用 `moheng_assistant` schema。
- **前端：** React/TypeScript、共享 UI 组件、项目上下文及 API client；UI 不能把会话 ID 或隐藏按钮当作权限凭证。

## 2. 统一身份、项目授权和审计

1. 所有业务读写必须在服务端验证用户身份、角色、项目成员关系及所需权限。
2. 会话、报表和单位经营档案中的跨项目汇总只限于当前账户可访问的数据；不能把“公司级”解释为自动读取所有项目。
3. 关键业务操作写入审计日志；发生身份歧义时保留待核验标记，不按名称相似度直接合并正式主体。
4. 提交人不得审批本人提交的业务；审批步骤按公司统一配置执行。
5. 已过账的财务记录不得原位覆盖，纠正通过追加式调整和审计实现。

## 3. 合同额与变更签证

- 原始合同基线与当前有效合同额分别保存。
- 变更签证的公司内部审批与外部业主/授权代表确认是两个独立环节；内部批准不等于外部确认。
- **有效合同调整依据：有效外部确认金额。** 补充协议可后续补办，不因此把尚未外部确认的内部审批金额提前计入有效合同额。
- 有效金额重算须排除删除记录、未生效外部确认和缺失有效确认金额的记录，并保留原值、重算值与 reason code。
- 如果内部批准额和外部确认额不同，应展示差额并留待业务复核；不能静默改写任一历史金额。

## 4. 业主侧结算、应收与现金流

- 进度款核定、竣工结算过账、获批调整和质保金释放是应收来源；实际到账与退款是独立现金流。
- 阶段结算通常表示本期增量；最终结算是最终累计确认额。最终过账以“最终累计额减既有已过账累计额”得到本次增量，不能将累计金额重复累加。
- 应收净额、未收余额、主合同净应收敞口、预付款和质保金余额分开核算。
- 退款须关联原到账并反向恢复原核销分配；应收核销受到单据余额和主合同余额的共同限制。

## 5. 分供合同、结算、应付与成本

- 分供合同原始额、当前有效合同额、结算额、应付额、发票额、现金付款和实际成本是独立事实。
- 没有结算明细行时，仍可通过结算单头金额完成业务；如提供明细，则需符合报审金额等业务校验。
- 只有符合流程且正式过账的结算才产生正式应付。负向调整可能形成待返还/抵扣余额。
- 付款核销到应付单；退款关联原付款并反向恢复核销。预付款进入独立预付款账本。
- 结算、发票与付款不得自动创建/冲减实际成本，以免重复计入经济成本。

## 6. 数据精度和主数据

- 金额在持久化与业务计算中使用 Decimal/整数分规则；避免将 JS 浮点结果直接用于关键金额运算。
- Excel 无法精确表示的超高精度金额应保留为文本，不可默默舍入。
- 正式往来单位优先按统一社会信用代码/已核验合同主体关联。由历史文本回填的主体须保持 `identityVerified=false`，待核验前不自动与正式主体合并。
- 成本关联了分供合同时，合同上的对方主体比冲突的旧自由文本供应商名更可靠；不应仅靠自由文本覆盖已核验关联。

## 7. 升级与恢复

- 迁移必须保留历史迁移文件，不重写已应用迁移；修复采用向前补丁。
- 先在一次性测试数据库和脱敏代表性预发布快照演练，逐项目对账后才可评估生产升级。
- 备份恢复需比较表清单和数据完整性，并测试权限、应用访问、附件目录与密钥恢复；CI 合成数据库演练不替代真实环境恢复审批。
