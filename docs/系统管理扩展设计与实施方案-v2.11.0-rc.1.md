# 系统管理扩展设计与实施方案（v2.11.0-rc.1）

## 1. 目标与边界

本版本将系统管理工作台从路线图入口扩展为可执行的管理界面与服务端 API，按账号安全、组织与授权、规则治理、运行维护、数据治理/集成五条主线组织。版本号为候选版本（RC），不是生产就绪声明；没有完成真实公网和目标部署环境验证，不能认为已经正式上线。

保持以下边界：

- 公司账号角色（`ADMIN`/`USER`）与项目内角色（`OWNER`/`MANAGER`/`ESTIMATOR`/`VIEWER` 等）仍为两种不同授权维度；部门/岗位只表达组织归属，不自动授予项目访问权。
- 变更签证规则当前只约束公司内部“谁可以审批/确认内部状态”。外部业主或授权代表确认的合同金额生效依据保持原有流程，不由新规则覆盖。
- 所有新管理 API 服务端强制验证会话并要求公司级 `ADMIN`，前端路由保护只是第二道防线。
- 集成凭据只返回是否已配置和版本等元数据，不返回明文；通用适配器当前尚无连接测试/真实同步执行能力。
- 备份文件落在部署指定的受控目录；“已备份”与“恢复验证通过”是两个不同状态。生产应用进程绝不应指向恢复演练库。

## 2. 五个优先级与本版本交付

### P1：账号与安全闭环

沿用 v2.10 已实现的个人修改密码、MFA 加强验证、会话/刷新令牌撤销、登录安全事件及操作审计，并对回归验证保留静态检查。账号停用时的最后一个启用管理员保护继续生效。系统管理扩展接口不绕过原有认证与 MFA 策略。

### P2：组织、角色与数据范围

新增部门树（编码唯一、父级有效、阻止循环）、部门启停和部门使用约束；账号可分配部门/岗位。该变更不改变公司级角色，也不创建项目成员关系。

项目范围仍由已有 `ProjectMember` 和服务端项目访问检查决定。当前提供的是“现有权限规则补齐 + 明确组织归属”，并非可任意配置的 ABAC/RBAC 引擎。本版本的变更签证内部审批规则仅允许 `OWNER`、`MANAGER` 两类项目角色组合配置，规则解析器拒绝 `VIEWER` 等不允许的角色。提交人不能审批本人提交的变更。

### P3：系统规则配置与版本发布

新增 `GovernanceRuleVersion`。变更审批规则必须经历“创建草稿 → 管理员发布”，每个规则键保留版本、状态、说明、创建人、发布人和时间。发布在可串行化事务中将旧版本退役并发布新版本；审批时的生效规则读取、项目成员角色检查、状态更新与审计也放入同一可串行化事务，避免并发发布/权限变更使用过期规则。并发冲突时返回错误并要求刷新，不静默覆盖。尚无已发布版本时回退到内置默认角色 `OWNER + MANAGER`。

规则当前只涉及内部变更审批角色，不配置合同金额、结算公式、税率、外部确认和财务规则。未来新增业务规则前必须另行定义 schema、模拟/回放、审批发布、回滚与审计验收。

### P4：运行维护与备份恢复

`GET /api/system-management/overview` 汇总应用版本、Node 版本、运行时内存/时长、数据库可用状态、后台任务状态、备份目录磁盘统计、`pg_dump`/`pg_restore`/`psql` 工具可用性、集成主密钥是否符合格式，以及备份和集成摘要。只显示布尔状态，不回显密钥或路径。无法连接数据库时仍尽可能返回运行时状态，不伪装数据库健康。

`POST /api/system-management/backups` 真实执行 `pg_dump` custom-format 备份，记录开始/结束、大小、SHA-256、结果和审计。命令不通过 shell 拼接执行；为子进程构造最小环境变量，避免传入应用的 JWT/MFA 等秘密。备份目录应由部署人员配置为绝对路径，Unix 部署会将备份目录权限收紧至 `0700`，并先以 `0600` 权限创建空文件再交给 `pg_dump` 写入，减少备份文件在写入期间被其他本机账号读取的窗口；Windows 原生部署仍需管理员在 NTFS ACL 中限制该目录和文件访问。

恢复演练不是向生产库恢复。它需要显式配置 `RESTORE_TEST_DATABASE_URL`，目标数据库名必须以 `_restore_test` 或 `-restore_test` 结尾，且源/目标主机 DNS 地址集合不得重叠。恢复前校验文件名、文件大小及 SHA-256，执行 `pg_restore` 后通过 `psql` 检查 `User`、`Project`、`MainContract` 等核心表。演练结果和失败原因均留存；成功验证的备份将被标记为已验证。

保留策略按 `BACKUP_RETENTION_DAYS`（范围 1–3650 天）清理旧成功备份，保留至少两个最新备份文件；清理后保留运行/审计元数据。过期清理失败不会把新备份伪装成失败，但会写受控日志供运维检查。

### P5：数据治理与集成管理

新增只读为主的数据质量扫描，并将每次执行写入审计。当前检查覆盖：项目缺少主合同、已确认变更缺少金额、外部金额确认缺少必要字段、金额差异待复核超过 30 天、管理员存在 MFA/初始密码待处理项、启用账号缺少部门，以及启用集成缺少凭据。单类最多返回 200 条并显示是否截断。

集成凭据通过 AES-256-GCM 加密，密钥从部署环境变量 `INTEGRATION_ENCRYPTION_KEY` 读取（64 个十六进制字符，即 32 字节）；使用随机 12 字节 IV，认证标签与集成编码/凭据版本作为认证上下文。数据库泄漏时仍需将数据库与主密钥分开保护。页面和 API 不回显密文或明文，提供显式凭据轮换和审计。该版本的 `secretVersion` 是单条集成凭据版本，不代表主加密密钥轮换版本。主密钥轮换/旧密文重封装流程需先完成独立迁移设计，切勿直接改环境密钥，否则既有密文将无法解密。

## 3. 迁移与部署参数

本版本新增 Prisma 迁移：`apps/api/prisma/migrations/20261016010000_system_management_expansion/migration.sql`。部署流程必须先备份数据库，再部署迁移，随后生成/更新 Prisma Client、部署 API/Web，并做冒烟验证。不得在生产环境直接运行恢复演练。

新增或需要确认的环境变量：

- `INTEGRATION_ENCRYPTION_KEY`：64 位十六进制 32 字节主密钥；通过密钥管理器/受控部署变量注入，不入库、不提交、不写日志。
- `BACKUP_DIR`：备份目录绝对路径（容器默认 `/app/backups`；原生部署示例 `C:/MohengBackups`），不允许指向文件系统根目录。目录应具备最小权限、容量监控和独立备份策略。
- `BACKUP_RETENTION_DAYS`：备份文件保留期，默认 30 天。
- `PG_DUMP_PATH`、`PG_RESTORE_PATH`、`PSQL_PATH`：可执行文件路径；默认依赖部署镜像中的 PostgreSQL client。
- `RESTORE_TEST_DATABASE_URL`：只允许指向独立、可丢弃的演练数据库。Docker Compose 提供 `restore-test` profile 服务，但 URL 必须由部署人员结合网络/凭据正确配置。

升级前必须确认数据库连接用户有备份与恢复演练所需权限，并检查生产与演练数据库隔离策略、网络策略和日志保留。部署环境若未配置密钥或恢复目标，相应功能会明确返回未配置/失败，不会假报成功。

## 4. API 一览

| 方法 | 路径 | 用途 |
|---|---|---|
| GET | `/api/system-management/overview` | 运行时、数据库、任务、磁盘和备份概览 |
| GET/POST/PATCH | `/api/system-management/departments` | 部门列表/创建/修改 |
| PATCH | `/api/system-management/users/:id/organization` | 分配部门/岗位 |
| GET | `/api/system-management/rules` | 规则历史与当前生效规则 |
| POST | `/api/system-management/rules/change-approval/drafts` | 创建变更审批规则草稿 |
| POST | `/api/system-management/rules/:id/publish` | 发布规则版本 |
| GET/POST/PATCH | `/api/system-management/integrations` | 集成配置元数据与启停 |
| POST | `/api/system-management/integrations/:id/rotate-secret` | 轮换单个集成凭据 |
| POST | `/api/system-management/data-quality/scan` | 运行一次数据质量扫描 |
| GET/POST | `/api/system-management/backups` | 查询备份记录/执行数据库备份 |
| POST | `/api/system-management/backups/:id/restore-drill` | 在隔离库执行恢复演练 |
| GET | `/api/system-management/backups/:id/download` | 校验后下载备份文件 |

## 5. 已知限制与后续阶段

- 部门/岗位已能维护，但尚无组织树批量导入、组织范围的数据权限继承、岗位模板和账号批量调配。
- 规则版本已有草稿/发布/审计和变更审批调用点，但没有通用规则引擎、多人会签、定时生效、回滚按钮或业务规则模拟器。
- 运维页面展示 API 进程和后台任务数据，尚未覆盖容器/主机完整健康、日志保留策略强制执行、外部监控告警及多节点任务一致性。
- 备份按单 API 进程任务执行，当前没有分布式锁、异地/对象存储复制、恢复后的完整业务抽样比对，也未接通调度器自动化定时备份。生产部署应由外部备份调度/保留策略兜底，并定期进行人工批准的灾备演练。
- 集成凭据目前是加密保管与轮换登记，还没有真实外部系统同步适配器、出站网络 allowlist、连接测试、超时重试、幂等和 webhook 签名验证。
- 数据质量扫描是按需执行和有限结果展示，不会自动修复业务数据，也不代替财务审计。

## 6. 验收原则

静态源码契约通过仅证明预期实现和关键防护存在，不代表编译、数据库迁移、真实 PostgreSQL 备份恢复、浏览器 MFA 流程或生产部署已验收。升级前应完成阶段验收记录中列出的阻塞项。候选版本在实际依赖安装、构建、测试及隔离环境演练之前，不得标记为生产就绪。
