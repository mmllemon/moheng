## 2. 第 22 步：1 条失效断言

### 症状

```js
check('legacy theme mapping and missing preview path are type-narrowed',
  authStore.includes("theme?: UiTheme | 'light' | 'dark'") && ...);
```

`apps/web/src/auth-store.ts` 中已无该片段。

### 判断依据（读代码，不是机械修）

实际实现是：

```ts
// auth-store.ts:81-83
const value = JSON.parse(raw) as Partial<UiPreferences> & { theme?: string };
const savedTheme = value.theme;
const theme: UiTheme = savedTheme === 'plain-white' || savedTheme === 'midnight' ? savedTheme : 'warm-paper';
```

**这个写法比断言假设的更强**：localStorage 里可能是任意脏值，不只是 `'light' | 'dark'`。
先当 `string` 读入、再逐个枚举比对收窄，是正确的防御方式。

断言原本想验证的意图（「legacy 主题值不能被原样接受」）仍然成立，只是匹配的字符串过期了。

### 修法

改断言，不改实现：

```js
const authStoreNarrowsLegacyTheme = authStore.includes("{ theme?: string }") &&
  authStore.includes('const savedTheme = value.theme');
check('legacy theme mapping and missing preview path are type-narrowed',
  authStoreNarrowsLegacyTheme &&
  authStore.includes("savedTheme === 'plain-white' || savedTheme === 'midnight'") &&
  authStore.includes('const theme: UiTheme =') &&
  designer.includes('!preview ? <ErrorBlock'));
```

**为什么不改实现**：让正确的类型收窄回退成硬编码联合类型，是为了让断言通过而降低代码质量。

结果：`23/23 passed`。

## 3. 第 23 步：4 条失败，性质各不相同

### 3.1 `--text` 被 var() 包裹（改断言）

```js
// 旧断言
hana.includes('--text: #3b3d3f')
// 实际
--text: var(--content-ink, #3b3d3f);
```

原因是字体对比度五档功能：`--content-ink` 随档位变化，兜底值仍是 Hana 真值 `#3b3d3f`。
这是功能需要，不是退化。断言改为接受两种写法。

### 3.2 `--accent` 断言标签不实（改断言标签）

旧标签写 `Hana 1.1.35 paper / ink / seal tokens are present`，
但它断言的是 `--accent: #466b80`，而 **Hana 真值是 `#537D96`**。

`#466b80` 是墨衡为达到 WCAG AA 有意压深的结果（设计文档 §4 已记录）。
断言本身没错，但标签声称「Hana tokens are present」是不实的。

改为 `Hana 1.1.35 paper tokens and intentional accent shift are present`，
并额外要求 `hana.css` 里保留 Hana 原值 `#537D96` 作为偏离依据。

### 3.3 字体断言查错文件（改断言）

```js
// 旧：只查 v6.css
v6.includes('MH Serif SC') && ... && v6.includes('notoserifsc.woff2')
```

实际情况：

- 三个字体文件都在 `apps/web/public/fonts/`（369KB + 18KB + 1.9KB）
- `@font-face` 已从 `v6.css` **迁到 `hana.css:6308`**（字体属于 Hana 设计层，v6 是旧层）

断言改为：字体族声明在 `v6 + hana` 任一处 + **字体文件实际存在**（用 `fs.access` 检查）。

**为什么加文件检查**：只看 CSS 里有没有 `notoserifsc.woff2` 这个字符串，
会出现「文件已删但 CSS 引用尚存」的假通过。

### 3.4 提示卡圆角（改断言 + 设计文档需订正）

```js
// 旧断言
hana.includes('border-radius: 10px')
// 实际
.inline-notice { border-radius: var(--radius-control); corner-shape: squircle; }
```

`--radius-control` 在 squircle 下解析为 `6 × 1.8409 ≈ 11.05px`，
不支持 `corner-shape` 时回退 6px。

**代码用 token 比硬编码 10px 更正确**，因为它能在 squircle 与降级间自动切换。
`docs/设计系统-hana.md` §6 写「统一为 10px 圆角」已过期，应订正为 `--radius-control`。

断言改为接受 token，并额外验证 `.sys-tabs` 是轨道形态（`corner-shape: squircle` 存在）。

结果：`75/75 passed`。

## 4. 附带修掉一个真实缺陷：`.sys-tabs` 三套定义

修断言时发现 `hana.css` 里 `.sys-tabs` 有**三套完整定义**：

| 位置 | 形态 | 是否生效 |
| --- | --- | --- |
| 3148-3154 | 单行压缩式，胶囊按钮 | 否 |
| 3234-3277 | 下划线 tab（`border-bottom: 2px`，38px 高） | 否 |
| **5229-5285** | **28px 轨道 + 2px 内边距 + 26px 滑块** | **是** |

CSS 后写优先，只有第三套生效。第三套恰好符合设计文档规格
（「28px 轨道 + 2px 内边距 + 26px 白色滑块」），前两套是淘汰的旧实现。

### 处理

删除 3148-3154、3234-3277，`hana.css` 从 6310 行降到 6259 行（删 51 行）。

### 为什么这次删是安全的

1. **人工确认边界**：3278 起是 `.sys-split`，与 `.sys-tabs` 无关
2. **删除前语法自检**：花括号 1989/1989 → 1975/1975，平衡
3. **删除后渲染比对**：26 路由视觉回归全绿，`tabs` 计数与删除前**逐项一致**

```
删除前: security=2, authorization=2, policies=2, governance=4, parameters=3
删除后: security=2, authorization=2, policies=2, governance=4, parameters=3
```

这条比对是关键：**删死代码必须证明渲染没变**，否则无法区分「删对了」和「删多了」。

### 过程中我犯的一个错

第一版脚本用启发式定位块尾（"遇到非 .sys-tabs 就停"），
误把 3243 的单行规则当块尾，结果只删 1 行、花括号失稳（1981/1982）。

**立即回滚**（有备份，一条 `Copy-Item` 恢复），改为人工确认边界后重跑成功。

教训：启发式定位在 CSS 这种交错结构里不可靠，宁可多花一次人工确认。

## 5. 元自检的改进

`validate-gate-integrity.mjs` 原先对 `--accent` 那条判 PASS，因为字符串确实存在。
但它验证的是「故意偏离 Hana 真值的值」，判 PASS 会掩盖这件事。

改为三类判定：

| 状态 | 条件 |
| --- | --- |
| PASS | 依赖存在且无偏离 |
| WARN | 依赖不存在（断言可能失效） |
| WARN | 依赖存在但属有意偏离（需人工确认偏离仍成立） |

现在如实报告两条 WARN：

```
WARN auth-store.ts 的 UiTheme 类型标注 已不在源码中（断言已同步更新，此处预期 WARN）
WARN hana.css 的 accent token 是故意偏离 Hana 真值的值
     mohengValue: #466b80  hanaValue: #537D96  理由: WCAG AA 4.5:1
```
