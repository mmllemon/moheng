# 门禁债务清单

本仓库有 35 条门禁，由 `scripts/run-gates.mjs` 逐项运行（不再是一条 `&&` 长串，第一项失败即全停）。
分级决定写在 `scripts/run-gates.mjs` 的 `GATES` 表（`tier` / `reason` 字段）。

```bash
node scripts/run-gates.mjs --list                 # 看门禁与分级
node scripts/run-gates.mjs --tier blocking        # 必须通过：失败即应拦 PR
node scripts/run-gates.mjs --tier advisory --capture   # 已知债务：摘要式明细
node scripts/run-gates.mjs --only architecture     # 单跑一条
```

CI 接入：`.github/workflows/source-gates.yml`。blocking 失败拦 PR；advisory 用
`continue-on-error` 不拦 PR，但每次都在 Job Summary 输出债务明细。

**`architecture`：硬编码计数改结构不变量**

原先断言 `moduleIds.length === 19` 与 `mountPrefix === 19 && integrationVisible: true === 16`；
模块由 19 增至 21（`workspace`、`project-artifacts`）后没人同步魔法数，门禁长红。现改为：

- 模块条目数 == 顶层路由插件数（`system-config.ts`、`assistant-conversations.ts` 属内联挂载例外）；
- 每个条目都声明 `mountPrefix` 与 `integrationVisible`；
- 不上集成目录的模块集合必须与显式登记名单逐个一致（新模块要隐藏就得加一行，而不是靠总数对不上）。

变异测试实测：新增一个可见模块 + 路由文件 → 两查仍通过，无需改门禁（即不再漂移）；
新增隐藏模块但未登记 → 失败；新模块漏写 `mountPrefix` → 失败。改后 11/11 通过。

### 3. 按决定保持 advisory 的两条（不修，但写清解除条件）

2026-10-29 决定：这两条停在 advisory，不进 blocking。理由与解除条件如下，避免以后被当成“漏修”。

**`source-bundle`：封版证据与当前 lock 不一致**

- 现象：根 `package-lock.json` 的 SHA-256 不等于封版记录里的期望值 `A6F8…`；基线 `3feb702` 的
  `575F…` 同样不等——即这不是本轮升级造成的。
- 为什么不是代码缺陷：它校的是“R7 封版当日的取证材料是否与今天的 lock 一致”。这是证据问题，
  改代码不能让它变绿，只能重新取证。
- 解除条件（必须全部做完，缺一步就是在造证据）：确认清单与 lock 来自同一实测工作树 →
  重新 clean install → `npm audit` → 两次 `npm ci` → 同时更新
  `scripts/validate-source-bundle-completeness.mjs`、`scripts/validate-public-access-security.mjs`
  里的期望值，以及 `docs/发布与迁移验收.md` 的记录。
- 风险提示：在它变绿之前，“可复现的封版产物”这个结论不成立。真要对外发布，这一步必须补。

**`gate-ui-parity`：已升为 blocking（2026-11-05）**

- 现象：仓库里只有 `docs/gates/ui-parity/web.json`，没有第二 target 的结果文件；门禁一直红着挂 advisory。
- 查清的根因（两层）：
  1. `scripts/_targets.mjs` 的 `launchTarget(kind)` 没有分支，web 与 electron 启的是**同一个** `CHROME_PATH`，
     且仓库无 electron 依赖、无 main 进程。就算生成 `electron.json`，也是“拿 Chrome 跟自己比”。
  2. `ui-visual-regression.mjs` 的 `TARGET=both` 只写 `both.json`，而门禁读的是 `web.json` + 第二 target 文件。
     也就是说，“按文档命令生成基线”永远拿不到门禁要的输入 —— 这才是“缺基线产物”的直接成因。
- 2026-11-05 的处理（owner 已明确桌面壳属于后续阶段）：
  - 第二 target 从 `electron` 改为 **`legacy`**：`_targets.mjs` 解析 `LEGACY_CHROME_PATH` → 本机
    `ms-playwright/chromium-*` 构建号最大者 → 交由 Playwright 解析。当前本机为 Chromium 149（web 是 Chrome 156）。
  - 结果按 target 分别落盘 `web.json` / `legacy.json`，`both.json` 只作人读合集。
  - 判等改成 squircle 感知：两侧都支持时圆角计数必须相等；legacy 不支持时改为断言“退化被如实记录”
    （`cornerShapeAccepted` 全为 false），tabs / 面板数 / 骨架 / 交互布尔量仍须相等。

## 已知上游告警（不是本仓缺陷，别误读成红）

**`pg` 的 `client.query() when the client is already executing a query`**

- 现象：跑 `test:downstream-payment:postgres`、`test:downstream-settlement:postgres` 时会打一条
  `DeprecationWarning`，测试本身全绿。
- 已定位到这层：调用栈落在 `@prisma/adapter-pg` 的 `PgTransaction.performIO → client.query`，
  再往上才是 `@prisma/client-engine-runtime` 的 `withChunkTransaction`，属于适配器把同一条连接上的
  查询串起来的实现细节，不是业务代码在事务里并发。
- 已排除的假设：用例里没有并发发请求（结算套件全程串行）；自写的诊断脚本在交互式事务里
  “先 `$queryRaw` 锁行再查模型”“事务内抛错回滚后立刻重开”“两个事务并发”三种写法都复现不出来。
- 同时修掉三处真实隐患：`downstream-contracts.ts`、`contracts.ts`、`projects.ts` 里各有一处
  `Promise.all([tx.a(), tx.b()])`。事务只有一个连接，在事务里并发发查询本身就是错的，已全部改成顺序 `await`。
  改完告警仍在，说明它与那三处无关，但三处该改。
- 处理：暂不 block；`pg@9` 升上去之前会变成真实错误，届时要顺带评估 `@prisma/adapter-pg` 版本。

## 升 / 降 tier 的规则

1. 一条 advisory 门禁修绿后，把 `GATES` 里它的 `tier` 改成 `blocking`，并在提交说明里带上修绿的断言。
2. 不要在门禁红着的时候把它从 CI 里摘掉——那等于让质量闭环再次静默。
3. 新增门禁默认 `advisory`，连续在 CI 里绿过若干次后再升 `blocking`，避免新写的断言一上来就阻塞所有人。
4. 禁止用“删除检查项”的方式让门禁变绿。
5. 若某条断言与另一条门禁互斥，禁令只由一条门禁持有，另一条改指现行实现，避免同一份代码
   永远无法同时满足。已知三次：`系统管理扩展入口`、`!important` 声明、原生 `window.confirm`。
6. 门禁指向“已按记录有意移除的结构”时，改写要保留禁令方向（写成显式负向断言），
   而不是把那条断言删掉；这样方向再变时会先红，而不是静默漂移。
