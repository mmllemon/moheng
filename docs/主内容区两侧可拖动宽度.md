# 主内容区两侧都可拖动宽度

日期：2026-10-24

## 结论

主内容区的**左右两侧都能拖动**，中间内容两头让位。

```
初始       侧栏 240  主内容 762  面板 580
左侧 +100  侧栏 340  主内容 662  面板 580
右侧 -150  侧栏 340  主内容 512  面板 730
```

两个宽度都持久化到 localStorage，刷新后保持。

## 左侧：Hana 有完整实现

`contributed-keybindings-BWxnaFR2.js`：

```js
const Ut = "--bridge-panel-left";
function Oa(e) { return `calc(var(--panel-edge-gap, 6px) * 2 + ${e}px)`; }

B = (width) => {
  aside.style.width = `${N}px`;
  overlayShell.style.width = `${N}px`;
  resizeHandle.style.setProperty('--fp-resize-left', `${N}px`);
  document.documentElement.style.setProperty(Ut, Oa(N));   // 主内容让位
};

D = useDrag({
  axis: "x",
  onStart: () => widthRef.current,
  onMove: ({ context, deltaX }) => B(context + deltaX),
  onEnd: ({ context, deltaX }) => { const N = clamp(context + deltaX); B(N); onWidthChange(N); },
  onCancel: () => B(widthRef.current),
});
```

把手 CSS：

```css
._fpResizeHandle {
  position: fixed;
  top: 6px;
  left: calc(6px + var(--fp-resize-left) + 3px);
  transform: translate(-50%);
  bottom: 6px;

._fpResizeHandle::after {
```

moheng 的实现（`lib/use-sidebar-resize.ts`）与之对齐，差异是 moheng 侧栏是 flex 子项，改 `--sidebar-width` 变量即可，不需要直接改 `aside.style.width`。

## 右侧：Hana 有把手元素但没有实现

这一项我查了三层，结论是**Hana 的右侧把手是死代码**：

**第一层：渲染层只有元素，没有绑定**

```jsx
h.jsx("div", { className: "resize-handle resize-handle-left", id: "previewResizeHandle" })
```

全库搜 `previewResizeHandle`：**只命中这一处 JSX 定义，没有任何 `getElementById` 引用。**

**第二层：宽度变量只读不写**

```js
function us() {
  return parseInt(getComputedStyle(document.documentElement)
    .getPropertyValue("--preview-panel-width")) || 580;
}
```

`--preview-panel-width` 在 JS 里只有这一处，**只读**。定义只有 CSS（`styles.css: 580px`）。

**第三层：主进程 bundle 也没有**

解出 `app.asar` 里的 `desktop/main.bundle.cjs`（1.23MB），搜：

```
previewResizeHandle   未找到
preview-panel-width   未找到
resize-handle         未找到
col-resize            未找到
```

**但把手元素本身存在，说明设计意图。** 而且 moheng 的预览卡固定 320px 时 PDF 只能显示半页，宽度可调有实际价值。所以把意图做成真的。

## 实现

新增 `lib/use-preview-panel-resize.ts`，与左侧对称：

| 项 | 左侧 | 右侧 |
|---|---|---|
| CSS 变量 | `--sidebar-width` | `--preview-panel-width` |
| 把手位置变量 | `--fp-resize-left` | `--preview-resize-right` |
| 范围 | 200 ~ 420 | **320 ~ 900** |
| 默认 | 240 | **400** |
| 存储键 | `cms:sidebar-width` | `cms:preview-panel-width` |
| 拖动方向 | 向右变宽 | 向左变宽（把手在面板左缘） |

**右侧的两个值来自 hana 的卡片 sizing 声明，不是 CSS**：

```js
// CardShell：预览卡注册
function Eit(n2) {
  return { ..., sizing: { role: "fixed", minPx: ZE, defaultPx: XE }, ... };
}
```

`ZE` / `XE` 是 import 的，原名 `h3` / `h2`，在 `index-DEPTMosq.js` 的导出表里：

```js
// 导出表
h3 → Cs    h2 → Ts

// 常量定义（同一行里的常量簇）
bm = 300, Cs = 320, Ts = 400, Dy = 290, Ny = 360, Oy = 440
```

所以：

```
minPx     = Cs = 320
 defaultPx = Ts = 400
```

**注意 `_previewPanel` 的 CSS 里没有 `min-width`**，宽度约束完全在 sizing 声明里，搜样式表是搜不到的。

`--preview-panel-width: 580px` 那个 CSS 值只是面板的默认显示宽度，与 sizing 的 defaultPx（400）不是同一个概念。

把手 CSS 逐字对齐 Hana 的 `.resize-handle-left`：

```css
.workspace-resize-handle {
  position: absolute; top: 0; bottom: 0; left: 0;
  width: 8px;
  z-index: 20;
  cursor: col-resize;
  touch-action: none;
}
.workspace-resize-handle::after {
  content: '';
  width: 3px; height: 44px;
  border-radius: 2px;
  background: var(--accent);
  opacity: 0;
  transform: translate(-50%, -50%) scaleY(0.12);
  transition: opacity .18s var(--ease-out), transform .18s var(--ease-out);
}
.workspace-resize-handle:hover::after,
.workspace-resize-handle:focus-visible::after,
.workspace-panel[data-resizing] .workspace-resize-handle::after {
  opacity: 0.35;
  transform: translate(-50%, -50%) scaleY(1);
}
```

**一处与 Hana 的差异**：Hana 的把手在 `left: -4px`（面板外侧），moheng 在 `left: 0`（面板内侧）。因为 `.workspace-panel` 有 `overflow: hidden`（用来裁切圆角卡片），放在外侧会被裁掉。

## 一个我凭感觉编的值

右侧面板的宽度范围，我第一版写的是 `360 ~ 900`、默认 `580`，理由是「与左侧对称」。**这是错的**——两侧的业务约束本来就不同，对称不等于正确。

真值在 hana 的卡片 sizing 声明里，不在 CSS 里：

```js
sizing: { role: "fixed", minPx: ZE, defaultPx: XE }
// ZE = h3 = Cs = 320
// XE = h2 = Ts = 400
```

已改为 `320 ~ 900`、默认 `400`。

**教训**：写范围值之前先找它的出处。找不到出处就标明「自定」，不要伪装成对齐。

## 一处我判断错的地方

上一轮你说「做反了，应该是主内容区右侧可拖动，而不是左侧」，我理解成「左侧那套是错的」，把侧栏拖动删了。

实际是「左侧对，右侧也要」。已恢复。

**教训**：用户说「A 不对，应该是 B」时，先确认是「A 该删」还是「A 之外还要 B」。这次的差别是全部删掉 vs 补一个。
