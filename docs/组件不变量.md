# 墨衡 · 组件不变量

这份文档回答一个问题：**改 UI 时，什么绝对不能破。**

`设计系统-hana.md` 记的是「值」——纸色是 `#F8F4ED`、侧栏 240px。
这份记的是「约束」——为什么按钮只有三个高度、为什么字号必须跟高度绑定、
为什么禁用按钮不许响应悬停。

值可以查，约束只能推。不写下来，下一个人就得重新推一遍，而且多半会推错。

> 状态（2026-10-22）：与 `scripts/` 下的常驻断言脚本一一对应。
> 文档和脚本不一致时，以脚本为准，并立即修文档。

## 1. 按钮高度：只有三档

| 高度 | 用途 | 字号 |
| --- | --- | --- |
| **32px** | 页头、对话框、区块主操作 | 13px |
| **26px** | 一般按钮、区块操作、台账工具条 | 11.5px |
| **24px** | 表格行内、密集操作 | 10.5px |

**不变量**

1. 全站每个 `.button` 的高度必须是 32 / 26 / 24 之一。
2. 同一个操作容器内，所有按钮高度必须相同。这条比第 1 条重要——用户看不出某个按钮是 26 还是 28，但一眼能看出同一行不齐。

**为什么是三档而不是两档**

最初收成 32/26 两档。表格行内按钮被迫用 26px 配 10.5px 字，和 `.button-small`
（26px 配 11.5px）撞车——同高不同字，并排就能看出来。所以行内单独降到 24px，
让高度和字号成对。

**踩过的坑**

`.button-small` 这个类名在三个文件里被定义过：

```
legacy.css:152   min-height: 28px; font-size: 10px
v6.css:255       height: 26px;    font-size: 11px
hana.css:915     height: 28px;    font-size: 11.2px
```

谁赢取决于加载顺序和上下文，所以**同一个组件在不同页面量出不同高度**。
现在用 `html` 前缀 + 显式 `min-height` 钉死。

还有一处更隐蔽：`hana.css` 里 `.ldg-tools .button-secondary { height: 28px }`
特异度 20，压过通用规则的特异度 11。这类「容器级覆盖」是按钮不齐的主要来源，
改高度时必须把容器规则一起改。

## 2. 按钮字号：跟高度绑定，不跟容器绑定

| 高度 | 字号 / 字重 | token |
| --- | --- | --- |
| 32px | 13px / 500 | `--btn-font-lg` |
| 26px | 11.5px / 500 | `--btn-font` |
| 24px | 10.5px / 500 | `--btn-font-sm` |

**不变量**

1. 字号由高度决定，不由所在容器决定。容器可以同时装主按钮和紧凑按钮。
2. 不新增第四档。需要更小的字时，先问是不是该换一种控件。

**为什么**

改造前 388 个文字按钮有 **22 种**字号/字重组合。根因是 `.button-secondary`
一个类在六个地方定义了六个字号：

```
v6.css:247                                    12px
legacy.css:2591 (.system-parameter-submit)    10px/600
hana.css .ldg-tools                           10.5px
hana.css .data-table                          10.5px
hana.css .system-dictionary-heading-actions   10.5px
hana.css .system-dictionary-item-actions      11.5px
```

每处都是「当时那个容器需要多大」。没有共享比例，同一个语义按钮换个位置就换字号。

Hana 的做法可以印证：它的按钮字号只走三个 token，
`--fs-hint` 用了 37 次、`--fs-caption` 17 次、`--fs-ui` 10 次，零处硬编码 px。

**注意 22 种里大部分不是 bug**

侧栏导航项 13px、下拉触发器 12.5px、报告分类标签 11px——它们长得像按钮但语义不同，
不该统一。判断标准是「同一高度是否配了不同字号」，不是「有多少种字号」。

## 3. 图标按钮：图标本体 + 内边，正方形

| token | 算式 | 结果 | 用途 |
| --- | --- | --- | --- |
| `--icon-btn-size-lg` | — | 32px | 标题栏、侧栏主控 |
| `--icon-btn-size` | `22px + 2×2` | 26px | 侧栏个人操作 |
| `--icon-btn-size-sm` | `18px + 2×2` | 22px | 侧栏项目操作 |

**不变量**

1. 图标按钮必须正方形（宽高差 ≤ 2px）。
2. 高度必须在 22 / 24 / 26 / 28 / 32 之内。
3. 尺寸从 token 推导，不写字面量。

**Hana 的原始算式**

```css
height: calc(var(--card-top-btn-size, 24px) + var(--card-top-btn-pad, 2px) * 2)
```

读法是「**图标 24px，给它 2px 呼吸空间**」。想整体缩放只改这两个变量，
所有图标按钮同步变。moheng 沿用了这个形状（`--icon-btn-pad` + 三档图标本体）。

**注意**

- Hana 的图标按钮**不是正方形**：`_fileOutputActionPrimary` 是 31px 宽、
  `_fileOutputActionMenuButton` 是 22px 宽，宽度跟着图标本身形状走。
  moheng 全部做成正方形，因为这里的图标都是等宽 SVG。
- `/reports/studio` 的 Univer 表格工具栏（24×30、24×16）**故意豁免**。
  那是第三方组件，改了升级会丢。`audit-icon-buttons.mjs` 里显式写明了这条豁免和理由。

**踩过的坑**

356 个图标按钮分散在 6 套并行类名里，只有 1 个用了共享的 `.icon-button`。
其中 `.titlebar-icon` 在 `hana.css` 出现两次（32px 和 28px），我一度判定为重复定义
并「修」了它——**那是错的**，第二个在 `@media (max-width: 680px)` 里，是窄屏故意收窄。

教训：看到两处同名定义，先查作用域，再判定是不是冲突。

## 4. 输入框高度：两档 + 嵌套算术

| 高度 | 用途 |
| --- | --- |
| **32px** | 一般输入、下拉触发器 |
| **26px** | 紧凑场景（设置页侧搜、字典项、助手密钥） |
| **72px** | textarea |

**不变量**

1. 高度必须是 32 / 26 / 72 之一。
2. **包裹框内的 input 高度 = 外框高度 − 2 × 外框边框宽度。**

第 2 条是最容易误判的地方。`.toolbar-search` 是 32px 的有边框容器，
里面装 30px 的无边框 input：

```
32px（外框） − 2×1px（边框） = 30px（内框）
```

这是**正确的**，不是 bug。审计脚本第一版没有把边框算进去，把这种正确嵌套报成了「内外不一致」——
如果照着改，input 会被撑破容器。

## 5. 输入框状态：三态必须可区分

| 状态 | 背景 | 边框 | 光标 |
| --- | --- | --- | --- |
| 可编辑 | `--bg-card` | `--border` | `text` |
| **只读** | 3.5% 半透明 | 55% 弱化 | **`default`** |
| **禁用** | 2% 半透明 | 40% 弱化 | **`not-allowed`** |

**不变量**

1. 只读和禁用必须有视觉区别，不能与可编辑同貌。
2. 只读用 `cursor: default`，**不用 `not-allowed`**——只读内容仍可选中复制。
3. 禁用态在 `:hover` 下不许有任何样式变化。

**为什么专门列这一节**

全站扫描 109 个输入控件，报告「0 个禁用、0 个只读」。这个 0 不是「没问题」，
而是「扫不到」——这些状态藏在数据条件和交互后面。

读源码找到 9 处，手工构造场景验证，触达的那处是坏的：
变更审批弹窗里的只读「内部送审金额」`opacity=1`、`cursor=text`、背景与可编辑输入完全相同，
唯一的差异是边框色，而那个颜色来自 `autoFocus`，跟只读毫无关系。

根因：`hana.css` 里原生 `input` / `select` / `textarea` **一条 `:disabled` 规则都没有**，
统一外观把浏览器自带的禁用渲染完全盖住了。

**判断「扫描结果为 0」的正确姿势**

先怀疑筛子，再下结论。

## 6. 交互状态

**不变量**

1. 所有 `:hover` 必须排除 `:disabled`，写成 `:hover:not(:disabled)`。
2. 禁用态在 `:hover` 下重复声明自身，防止后续 hover 规则推动它。
3. `:focus-visible` 必须有可见轮廓。鼠标点击不触发，不影响指针用户。

**hover 各变体变化的维度**（不是所有按钮都该三色联动）

| 变体 | 变化维度 | 理由 |
| --- | --- | --- |
| 主按钮 | 背景 + 边框 → `accent-hover` | 实心块，边框属于背景 |
| 次按钮 | 背景 + 边框由透明升到 11% | 原来边框塌成透明，悬停像「散了」 |
| 幽灵按钮 | 背景 + 边框 9% + 文字 | 原来只有一块浮起来的底色 |
| 危险按钮 | 三色一起向红靠 | 语义需要强调 |

**为什么保留三色联动而不是全站统一**

查 Hana 时发现 `.hs-button:hover` 很克制——只改背景。三色联动是它
**应用层图标按钮**的做法，不是设计系统按钮的规则。照搬「三色」到所有按钮是读错了。

**踩过的坑**

全站 70 条 `:hover` 里只有 4 条排除 `:disabled`。禁用按钮悬停时背景从 3% 变亮到 8%，
**看起来像能点**。实测 `/system/dictionaries` 的「保存资料」按钮，
明明 `opacity: 0.5`，鼠标放上去背景还是变。

这类问题截图完全看不出来，只有把状态激活了去测才会暴露。

## 7. 圆角：5px × 1.84，且必须 `@supports` 门控

```css
:root { --corner-radius-scale: 1 }
@supports (corner-shape: squircle) {
  :root { --corner-radius-scale: 1.8408964152537137 }
}
```

**不变量**

1. `1.8409` 必须包在 `@supports (corner-shape: squircle)` 里，不能无条件生效。
2. 圆角从 `--radius-*` token 推导，不写字面量。

**为什么是 1.84**

`squircle`（超椭圆）在相同半径下比普通圆角「看起来更方」。要让 squircle 的观感
和普通圆角的圆润度相当，半径就得放大。`1.8408964152537137` 是这个补偿量。

支持 squircle → 1.84，squircle 补偿，视觉与 Hana 一致。
不支持 → 1.0，普通圆角回到 5/6px，观感反而更接近 Hana。

**我说错过两次，都记在这里**

第一次：我判定这个值「没有来源、是魔法数字、该改回 1.0」。错在只搜了字面值，
没看它所在的声明块。

第二次：我判定 moheng「漏了 `@supports`」。错在只 grep 了 `--corner-radius-scale`
这个变量名，它周围三行就在那里，我没读。

两次都是同一个毛病：**grep 到关键词就下结论，没读完整声明块。**
涉及 token 和机制判断时，必须读完整个块再开口。

## 8. 统计卡与数据块

**不变量**

1. 布局用 `gap`，不用 `margin`。Hana 的 CSS 里 `gap` 出现 998 次、`margin` 732 次，
   间距几乎都由 flex/grid 的 gap 表达。
2. 统计卡容器 `repeat(3, minmax(0, 1fr))`，**不加媒体查询**。
   Hana 的 `.hs-metrics` 只有一条规则，没有任何断点。窄屏改为横向滚动。
3. 多行统计块用逐行 `:nth-child` 规则处理分隔线，不能用 `:first-child`/`:last-child`
   ——那只能处理单行。

**踩过的坑**

我一开始给 `.hs-metrics` 加了个两列断点，Hana 里没有这个东西。结果是宽屏下第二行
出现游离的分隔线。

## 9. 覆盖层债务（当前最大风险）

**现状**

七轮按钮/输入框改造，全部写在 `hana.css` 的覆盖层里。
`legacy.css`（308KB / 2850 条规则）和 `v6.css`（93KB / 975 条）一条没少。

实验证据（`test-layer-dependency.mjs`）：把我改动过的 5 个页面禁用 legacy 层，
**零差异**。说明被压着的旧规则还活着。

**这意味着**

继续按「下一个组件」往下修，覆盖层会越积越厚。
每一轮都在让页面变好看，同时让以后真正迁移变难。

**退役路线（未执行）**

不要全量迁移（3260 处 diff）。按「已被完全覆盖的组件族」逐个删：

1. 用 `data-*` 标记出哪些旧规则从来没生效过
2. 删掉，验证零差异
3. 挑一个族做真迁移试点（建议 `.button` 家族）：把旧层里仍生效的规则**搬进** `hana.css`，删掉旧层原件
