# 结算与应付账款模型设计说明

- 系统：墨衡｜施工单位成本管理系统
- 版本：MVP 1.4.0-rc.1 验证候选
- 范围：分供合同结算、应付账款、付款核销、预付款、质保金、供应商发票

## 1. 设计目标和不变量

本模块把分供合同的履约金额确认和现金支出分开建模。合同金额、结算金额、应付金额、发票金额、实际付款和实际成本是不同的业务事实，不能彼此替代。

必须遵守以下不变量：

1. **结算清单项可选，不是业务前置条件。** 没有合同清单、预算清单或清单编码时，允许使用结算单头的汇总金额完成建单、提交、内部审批、外部确认和过账。明细行不引用 `BudgetItem`，不要求合同清单记录存在。
2. 如果提交了可选明细行，明细金额合计必须等于报审金额；没有明细行时不运行明细合计校验。数量、单位、单价均为辅助描述字段，不是结算金额计算必须依赖的数据。
3. 阶段结算金额表示本期增量；最终结算确认金额表示最终累计金额；调整单是正负金额增减。不得将最终累计金额再次全额累加。
4. 只有外部对方确认资料录入且结算正式过账，才创建应付账本记录。草稿、提交、内部审批和外部确认但未过账的金额不会计入正式应付余额。
5. 普通付款核销到一笔或多笔已过账应付单；分配金额合计必须等于本次付款金额，且不能超过应付未付余额。合同预付款不直接核销应付，而进入预付款余额。
6. 退款必须关联原始付款；对已有应付核销的付款，退款会按原分配记录反向恢复核销余额。原付款与退款都保留独立流水。
7. 结算、发票和付款不自动创建或冲减 `CostEntry`。实际成本按企业确认的成本过账规则独立录入和调整，以免重复入账。
8. 已过账记录不得原位修改/删除。更正须采用结算调整及对应审计记录。

## 2. 业务关系

```text
DownstreamContract（分供合同）
  ├─ DownstreamContractSettlement（阶段/最终/调整结算单头）
  │    ├─ DownstreamSettlementLine（可选明细；没有行也有效）
  │    └─ DownstreamSettlementPosting（不可覆盖的累计前值/增减/累计后值快照）
  │         └─ 正式过账时生成 DownstreamPayable（应付单）
  │              └─ DownstreamPayableSchedule（可选分期到期安排）
  ├─ DownstreamContractPayment（真实现金流）
  │    └─ DownstreamPaymentAllocation（付款到应付/具体期次的签名核销分配）
  ├─ DownstreamRetentionMovement（质保金留置/释放/核销流水）
  │    └─ 释放时生成 DownstreamPayable
  └─ DownstreamSupplierInvoice（供应商发票）
       └─ DownstreamInvoiceAllocation（发票金额分配到应付来源）
```

核心实体：

- `DownstreamContractSettlement`：编号、类型、状态、报审金额、外部确认金额、过账增减、预付款扣回、质保金留置、其他扣款、净应付、到期日、外部确认依据、流程人员与时间、驳回原因。
- `DownstreamSettlementLine`：可选的描述、数量、单位、单价、金额与排序；不依赖预算清单/合同清单。
- `DownstreamSettlementPosting`：一笔已过账结算的唯一过账快照，记录过账前累计值、本次增减和过账后累计值，避免后续重算/重复过账时丢失历史基线。
- `DownstreamPayable`：正式应付来源、应付基数、扣回/留置/扣款、应付净额、到期日、过账时间。负向调整允许形成供应商待返还/抵扣余额。
- `DownstreamPayableSchedule`：可选的应付到期分期。设置后各期金额之和必须等于应付净额；结算设有到期日时自动生成一期，未发生任何付款/退款核销前可改为多期。
- `DownstreamPaymentAllocation`：用签名金额连接现金流付款、应付单和可选的应付期次；正数消减未付应付及该期余额，负数表示退款反向恢复原期次。
- `DownstreamRetentionMovement`：`RETAIN`、`RELEASE`、`FORFEIT` 三类质保金变动；释放时生成质保金应付单，之后仍需实际付款。
- `DownstreamSupplierInvoice` 与 `DownstreamInvoiceAllocation`：分开记录发票接收/核验状态和发票对应付来源的分配，不与付款核销共用金额列。

## 3. 金额口径与计算

金额在数据库使用 `DECIMAL(18,2)` 保存。业务计算按整数分完成，展示时再转换。

### 3.1 当前有效合同金额

`当前有效合同金额 = 原始合同金额 + 已生效补充协议净额`

该金额描述合同商业基准，不自动成为每一笔应付或付款的金额。

### 3.2 累计结算金额和过账增减

设过去已经过账的结算累计净额为 `S_previous`：

- `PROGRESS`：`postedDelta = 本期外部确认金额`。
- `FINAL`：`postedDelta = 最终累计外部确认金额 - S_previous`。
- `ADJUSTMENT`：`postedDelta = 调整单确认的正/负金额`。

所有过账后的结算增减合计不得使累计结算金额低于零。同一合同只能有一笔已过账 `FINAL`；最终结算后的更正走 `ADJUSTMENT`。

示例：阶段结算 300,000 元、200,000 元，累计 500,000 元；最终累计确认 470,000 元，则最终结算只过账 -30,000 元，累计数变成 470,000 元，而不是 970,000 元。

### 3.3 正向结算应付净额

`应付净额 = 本次正向过账增量 - 预付款扣回 - 质保金留置 - 已批准其他扣款`

扣回、留置与扣款均不得为负，且总额不超过本次正向结算增量。预付款扣回不能超过当前可扣回预付款余额。负向结算调整不允许再次录入这些扣减项，以免双重扣减。

### 3.4 应付未付余额

`应付未付余额 = 应付净额 - 该应付单的有效付款核销净额`

付款分配为正数；退款反向分配为负数。负向应付调整显示为供应商待返还/抵扣余额，不与正向应付未付简单抵销隐藏。当前系统可展示此类余额，但自动与另一笔应付抵扣的工作流尚未实现。

### 3.5 预付款与质保金

- `预付款余额 = 已支付预付款 - 对应预付款退款 - 已过账预付款扣回`，不得低于零展示余额。
- `质保金余额 = 留置额合计 - 释放额合计 - 经批准核销/扣罚额合计`，不得释放或核销超过现有余额。
- 质保金释放生成新的应付单，释放本身不是实际付款。

### 3.6 发票核对

发票金额和税额分开记录。发票需先被登记并核验通过，之后方可分配到同一合同下的正向应付来源。累计发票分配不超过发票价税合计，也不超过该应付来源的正向应付基数。发票核对不自动完成应付确认、付款或实际成本过账。

## 4. 状态机

```text
DRAFT → SUBMITTED → INTERNAL_APPROVED → COUNTERPARTY_CONFIRMED → POSTED
   ↑           │                  │
   └── REJECTED ←─────────────────┘
```

- 创建结算单为 `DRAFT`。提交进入 `SUBMITTED`。
- `SUBMITTED` 只能由另一名有权限人员审批；提交人不能审批自己提交的单据。
- 内部审批后登记外部对方确认参考和日期，进入 `COUNTERPARTY_CONFIRMED`。
- 只有 `COUNTERPARTY_CONFIRMED` 能过账。过账在一个数据库事务内计算增减、生成应付/质保金流水、更新结算状态和写入审计。
- `SUBMITTED` 和 `INTERNAL_APPROVED` 可以按原因驳回；`REJECTED` 可编辑回 `DRAFT` 并重新提交。
- 过账后不允许原位编辑。调整单可以正向补增，也可以负向冲减。
- `FINAL` 仅允许合同处于完工待结算，成功过账后合同变成 `SETTLED`。阶段结算仅用于执行中/完工待结算合同。调整仅用于完工待结算或结算已确认合同。

## 5. 付款核销与退款

当合同存在已过账应付单时，普通的进度款/结算款/其他款需指定一个或多个应付来源；多笔分配合计必须与实际付款金额相等。付款时核验应付来源属于同一合同，剩余额度足够。质保金付款只能核销质保金释放来源。

合同预付款保留为未核销的预付款现金流，不能直接核销结算应付；未来结算通过 `advanceRecoveryAmount` 扣回。退款选择原始付款后，系统按原付款应付核销分配反向创建签名负数分配，恢复对应应付余额，但原始付款不删除。

历史系统中无可靠应付匹配关系的付款继续保留为历史未核销付款或预付款，不能仅因供应商、金额相似就自动冲配。操作人员应依据银行流水、付款申请与合同资料人工审核。

## 6. 权限、并发与审计

- 业务写入需通过项目成员权限检查与对应写角色检查。
- 结算/付款/发票/质保金更新在事务内处理；关键合同使用行级 `FOR UPDATE` 锁，金额过账与分配使用 Serializable 事务，冲突应刷新重试。
- 合同内结算编号、应付编号、发票号码、原付款参考号和各分配关系使用唯一约束防重复。
- 新增、提交、内部审批、外部确认、驳回、过账、发票核验与分配、质保金释放/核销等操作写 `AuditLog`。
- `postedAt`、人员与凭证引用用于追溯；过账记录不物理删除。

## 7. 新增迁移与兼容策略

新增迁移：`20261014010000_settlement_payables_invoice_retention`。该迁移包括结算过账快照、可选应付分期表和期次核销外键。

- 不修改以前发布的迁移文件；通过新增迁移添加结算、应付、付款核销、质保金、发票和分配关系。
- 不自动把历史付款与新应付单按名字或金额匹配；没有足够证据的历史记录保留未核销并由经办人核对。
- 原合同金额、有效补充协议与原付款记录保持不变。
- 部署前备份 PostgreSQL；部署时执行 Prisma Client 生成和 `prisma migrate deploy`，完成后逐项核对迁移状态与关键台账。

## 8. 当前边界和上线前必须验证的内容

该版本仅完成源码级发布候选，不应未经集成验收直接用于正式财务关账。当前候选环境尚未完成完整依赖安装、Prisma Client 生成/validate、完整 TypeScript 类型检查和生产构建、真实 PostgreSQL 迁移、Windows 浏览器交互与端到端验收。

目前没有落地的能力包括：供应商负向调整的自动跨应付抵扣/退款工作流、完整的收货/验收/退货与发票三单匹配、专业总账凭证与税务处理、主合同侧竣工结算与应收账款、自动成本暂估与冲销过账。应付台账不等于完整会计总账；发票分配也不等于会计确认。

正式上线前至少回归：纯金额结算、明细合计校验、阶段加最终差额、过账快照一致性、正负调整、提交人自审拦截、驳回后重提、预付款扣回上限、质保金余额、应付分期金额合计和到期核销、退款反冲至原期次、发票分配上限、并发重复过账、项目权限隔离、历史未核销付款留存。


## 8. v1.4.0 统一往来单位关系

结算/应付模型与统一往来单位主数据协同工作：分供合同 `DownstreamContract.counterpartyPartyId` 指向 `BusinessParty`；单位页沿该关联汇总已过账结算、应付余额、付款/退款、发票及合同成本。原 `counterpartyName` 保留为历史合同显示快照。

单位身份核验与合同是否已签订属于不同概念。迁移从历史文本名称建立的关联默认未核验，单位经营档案必须显示待核验警示。单位页按当前用户项目权限聚合；收入侧主合同和支出侧分供合同单独呈现，不自动做会计抵销。

本版新增迁移 `20261014020000_business_party_master`，不得修改先前迁移文件。其回填关系基于规范化名称，只是便于迁移后检索和人工复核的起点，不等于法律主体已完成验证。参见 `往来单位主数据与经营档案设计说明-v1.4.0-rc.1.md`。
