# 阶段验收记录

- 系统：筑衡｜施工单位成本管理系统
- 版本：MVP 1.5.0-rc.1 验证候选
- 阶段：源码静态检查与发布包整理，非生产验收通过版

## 本版本范围

1. 修复往来单位编辑弹窗的内部滚动区域和底部操作区布局，避免长表单使保存/取消按钮被挤出可视区域。
2. 建立业主侧最终竣工结算、结算调整、应收账款、分期、到账/退款、预付款与质保金释放模型；进度款核定可形成应收，最终结算按累计金额与历史累计的差额过账。
3. 主合同最终结算过账后，进度款旧入口停止直接收款；普通到账需要同时通过应收单余额与主合同净应收敞口校验。负向调整单独展示，不隐去历史记录。
4. 分供合同与付款、结算与应付在同一工作台入口下合并为两个明确子视图，而不是把所有表格堆到同一长页面。
5. 项目工作台导航按“业主侧 · 收入”与“成本支出侧”分区，以小标题、间距和视觉分隔形成语义分组。
6. 业务编号使用数据库序列按项目/类型/年份生成；合同编号字段仍允许手工提供外部或归档编号。数据库 ID 仍为关联主键。
7. 登录页增加记住账号。密码交由浏览器/操作系统密码管理器的标准保存与自动填充机制处理，不在应用 localStorage 明文保存密码。

## 已执行检查

- 旧版本已交付迁移的内容校验保持不变；新业主财务与进度款退款历史列通过新增迁移添加。
- `scripts/validate-release-candidate.mjs` 对版本、业务路由、静态 SQL/模型结构、导航、编号和登录策略做机械检查。
- TypeScript/TSX 通过全文件语法转译解析检查。
- 纯逻辑单测覆盖最终结算差额、正负调整、合同净应收敞口和应收状态。
- ZIP 发布包通过压缩完整性检查。

## 尚未执行/生产验收前置项

由于当前执行环境 Node.js 为 22.x，而项目要求 Node.js 24+，且完整依赖未安装，本轮尚未完成：完整 `tsc` 类型检查、API/Web 生产构建、Prisma `validate`/`generate`、真实 PostgreSQL 迁移与数据回填、Windows 浏览器交互/E2E、并发压测及真实备份恢复演练。因此这些检查不能被描述为通过。

## 重点未决业务边界

- 负向应收调整可被显示并纳入主合同净应收敞口的收款限制，但尚无自动创建跨应收单抵销凭证的完整工作流。
- 业主侧暂未实现完整会计总账凭证、税务、银行对账与收入确认政策。
- 记住账号只保留邮箱，密码依赖浏览器/操作系统密码管理器；应用不保存明文密码。
- 旧单位档案按历史名称回填的主体身份必须经人工核验，不得直接用于未经复核的供应商对账。
- 历史应收回填对缺少可靠主合同关联或金额依据的进度款不作猜测补录。

## Windows 验收建议

1. 在 Node.js 24+ 环境执行依赖安装、Prisma Client 生成、`prisma validate`、新迁移部署与生产构建。
2. 使用数据库备份副本检查旧数据回填、外键、唯一约束及编号序列。
3. 验证进度款核定→应收、阶段结算→最终累计差额、负向调整后收款上限、分期核销和退款反向恢复。
4. 验证单位编辑长表单、合并后的支出模块页签、收入/支出导航、自动编号、记住账号和浏览器密码管理器。
5. 验证同一用户跨项目权限、不同用户权限、单位汇总和原始单据的可见范围一致。
6. 通过回归及备份恢复后，才评估是否去掉 `rc` 标识。
