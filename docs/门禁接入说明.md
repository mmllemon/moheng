# 发布门禁接入说明

> 记录双 target 一致性检查如何接入 `validate:release-candidate`，以及为什么这样接。
> 更新日期：2026-10-23。

## 1. 接入的两个步骤

`validate:release-candidate` 从 33 步变成 35 步，新增：

| 位置 | 脚本 | 作用 |
| --- | --- | --- |
| 第 24 步 | `scripts/gate-ui-parity.mjs` | 双 target（web / electron）一致性门禁 |
| 第 25 步 | `scripts/validate-gate-integrity.mjs` | 门禁元自检：确认检查本身没失效 |

放在 `validate-ui-polish.mjs`（第 23 步）之后，因为三者都属于 UI 质量域。

## 2. 为什么需要一个包装器，而不是直接接入

`validate-ui-parity.mjs` 在缺少输入时会输出 `SKIP` 并 **exit 0**。

这对本地开发是正确的：没跑过浏览器不该报错。
但对发布门禁是致命的：**exit 0 就是"通过"**。

如果直接把 `validate-ui-parity.mjs` 放进链路，那么在没有 `electron.json` 的情况下，
门禁会显示绿灯，而实际上「桌面端一致性从未被验证过」——
比没有这道检查更糟，因为它给了虚假的安全感。

`gate-ui-parity.mjs` 的职责就是堵住这个洞：

```
输入缺失
├─ 默认                    → exit 1（判定失败，给出生成命令）
├─ PARITY_NOT_REQUIRED=1   → exit 0（放行，但打印双重警告）
输入齐全
└─ 结构校验通过 → 交给 validate-ui-parity 判等，透传退出码
```

## 3. 显式跳过开关

桌面端尚未开始时，允许显式声明：

```powershell
PARITY_NOT_REQUIRED=1 npm run validate:release-candidate
```

它会放行，但打印：

```
⚠ PARITY_NOT_REQUIRED=1 已设置，本次放行。
⚠ 这意味着桌面端一致性**未经任何验证**。发布说明中必须写明这一点。
```

设计立场：**跳过可以，但必须明确说出跳过了什么**。
不允许通过删除检查项来绕过——那会让这条门禁永久失效。

## 4. 门禁元自检查什么

`validate-gate-integrity.mjs` 共 4 项检查 + 1 组脆弱断言抽样：

| 检查 | 意图 |
| --- | --- |
| 双 target 门禁能被注入的差异触发失败 | 调用 `selftest-ui-parity.mjs`，确认 5 种人造差异全部被抓 |
| 双 target 门禁在输入缺失时不谎报通过 | 这是本轮修过的一个真实缺陷：`SKIP` 之后曾打印「全部通过」 |
| 运行环境契约单测可通过 | 确认 `runtime-contract.test.ts` 12 项能跑 |
| 脆弱断言抽样 | 检查断言依赖的源码片段是否还在 |

### 为什么要查「脆弱断言」

本仓库已经出现过两次同类问题：

1. `validate-ui-polish.mjs` 断言 `hana.includes('--accent: #466b80')` ——
   这是 moheng 自己改过的值，不是 Hana 真值 `#537D96`。改回真值反而 FAIL。
2. `validate-typescript-fixes.mjs` 断言 `auth-store.ts` 含 `theme?: UiTheme | 'light' | 'dark'` ——
   实际已不存在，该断言稳定失败。

两次都是「检查在跑、结果有反馈、但验证的东西已经不是它以为的东西」。

元自检把这些变成显式的 `WARN`，而不是静默。

## 5. 当前真实状态（2026-10-23 实测）

```
第 22 步 validate-typescript-fixes.mjs   exit=1  ← 既有失败，与本轮改动无关
第 23 步 validate-ui-polish.mjs          exit=1  ← 既有失败（4 项），与本轮无关
第 24 步 gate-ui-parity.mjs              exit=1  ← 预期：electron.json 不存在
第 25 步 validate-gate-integrity.mjs     exit=0  ← 通过
```

**要点：`validate:release-candidate` 在本轮改动之前就已经是红的**（第 22 步即失败），
新增的第 24 步没有引入新的阻塞。两者失败原因不同、互相独立。

### 第 22 步失败原因

```js
// scripts/validate-typescript-fixes.mjs
check('legacy theme mapping and missing preview path are type-narrowed',
  authStore.includes("theme?: UiTheme | 'light' | 'dark'") && ...);
```

`apps/web/src/auth-store.ts` 中已无 `UiTheme | 'light' | 'dark'` 片段。
本轮未修改该文件（`git status` 可证）。属于历史遗留的失效断言。

### 第 23 步失败原因

4 项，已在上一轮审查中报告：

```
FAIL Hana 1.1.35 paper / ink / seal tokens are present
FAIL V6 serif and brush fonts are declared
FAIL Hana segmented tabs and tinted notes are wired
FAIL business party picker is a keyboard combobox
```

前三条是「检查项没跟上实现」（大小写、可变字体方案），第四条是真实功能缺口。

## 6. 让链路变绿需要做什么

按依赖顺序：

1. **修第 22 步的失效断言**（约 10 分钟）
   要么给 `auth-store.ts` 补回类型标注，要么删掉这条断言——
   取决于那个类型标注是否还该存在。这需要读代码判断，不能机械修。

2. **修第 23 步的 3 条检查项失配**（约 1 小时）
   把断言从源码文本匹配改为读取 Hana 真值，或跟随实现更新。

3. **补第 23 步的真实功能缺口**（半天）
   `BusinessPartyPicker` 的 combobox 键盘支持。

4. **生成 electron.json**（取决于桌面端进度）
   在 `desktop/` 建好之前，只能用 `PARITY_NOT_REQUIRED=1` 显式跳过。

## 7. 一个建议

第 25 步的「脆弱断言抽样」目前只登记了 2 条。
后续每新增一条依赖源码文本的断言，都应同步加进 `fragileAssertions` 数组，
否则元自检会随着时间失去覆盖面。

这个数组本身也需要定期对照 `validate-*.mjs` 全量清单核查一次。
