# 往来单位主数据与经营档案设计说明

- 系统：筑衡｜施工单位成本管理系统
- 版本：MVP 1.4.0-rc.1 验证候选
- 范围：统一单位主档、业务角色、合同关联、单位经营档案、跨项目汇总与权限

## 1. 设计结论

建立统一的 `BusinessParty` 主档，而非建设单位库、材料供应商库、分包商库三套互不关联的主数据。一个法律主体可以具有多个业务角色；各业务单据通过单位 ID 关联，同时保留合同/成本记录中的文本名称快照。

这一模块既为录入减少重复，也为公司级跨项目单位查询提供唯一可追溯的聚合入口。单位身份、合同状态、结算状态、应付状态、发票状态和成本事实是不同维度，不得合并为单一状态。

## 2. 核心数据模型

### 2.1 `BusinessParty`

- 标识：`id`、显示全称 `name`、检索规范化名称 `normalizedName`。
- 身份：`creditCode`（可空、全局唯一）、`identityVerified`、`identityVerificationNote`、`formerNames`。
- 角色：`BusinessPartyRole[]`，包括 `OWNER`、`MATERIAL_SUPPLIER`、`LABOR_SUBCONTRACTOR`、`PROFESSIONAL_SUBCONTRACTOR`、`EQUIPMENT_LESSOR`、`SERVICE_PROVIDER`、`OTHER`。
- 管理：`status`（ACTIVE/INACTIVE/ARCHIVED）、地址、联系人、电话、邮箱、法定代表人、税号、开票抬头和备注。
- 审计：创建/更新时间和 `AuditLog` 记录。

`normalizedName` 不能建立唯一约束，因为同名的两个法律主体可能确实不同；统一社会信用代码建立唯一约束。检索名称只帮助匹配，不替代法律身份核验。

### 2.2 业务关联

- `Project.ownerPartyId`：建设单位关联。
- 主合同相对方复用项目的建设单位关联，避免主合同与项目建设单位出现互相矛盾的两个主档来源。
- `DownstreamContract.counterpartyPartyId`：分供合同的供应商/分包/租赁/服务单位。
- `CostEntry.businessPartyId`：没有关联合同时记录成本往来单位；如果成本已关联分供合同，则合同相对方是权威单位关系。
- 原文本 `Project.ownerName`、`DownstreamContract.counterpartyName`、`CostEntry.vendorName` 保留，作为历史业务显示快照，不因单位主档更名而批量覆盖。

## 3. 合同登记和快速建档

合同录入通过单位名称/信用代码搜索已有单位。选择后带出已维护的基础信息；没有匹配项时可以启动快速建档，并在业务保存时创建/复用主档及合同关系。系统不应在用户打字或离开输入框时自动写入不完整单位记录。

- 传入明确 `partyId` 时，后端验证该单位存在且处于 ACTIVE。
- 仅传名称时，后端按规范化名称检索：0 条则建立待核验单位，1 条则复用并补充业务角色，多于 1 条则拒绝模糊匹配，要求用户明确选择。
- 同名不同主体的新增仅允许管理员执行，并要求独立的唯一统一社会信用代码与明确确认。
- 单位身份核验仅限管理员，必须记录可审计的核验依据。合同表单直接以自由文本提交时，服务端可在业务保存事务内复用/创建单位；若用户主动在“新建往来单位”快速建档弹窗中先保存主档，则它独立存在于单位库，即使随后合同未保存成功也不会回滚，这属于显式创建单位档案的结果。
- 基础单位信息可自动带出，但合同编号、合同金额、合同日期、项目范围、付款条款仍由当前合同自己的业务事实决定。历史签约文本不因后续单位地址/名称更新而变更。

## 4. 单位经营档案

### 4.1 页面及入口

左侧导航“往来单位库”用于搜索、按角色筛选及维护单位主档。单位名称在项目、主合同、分供合同、独立成本等页面可点击并进入 `/parties/:id` 单位经营档案。

单位经营档案包括：

1. 单位基本资料、角色、当前状态、信用代码及身份核验状态；
2. 经营摘要；
3. 关联项目列表及项目维度摘要；
4. 主合同及收入侧进度款、收款、变更摘要；
5. 分供合同、阶段/最终结算、应付未付、供应商待返还/抵扣、付款/退款、发票和合同关联成本；
6. 未关联合同的独立成本记录聚合；
7. 逐项进入项目、合同或业务单据的入口。

收入侧与支出侧数据分别展示。不得把合同当前金额等同于已实现收入、把付款等同于成本，也不得简单将收入合同金额减支出合同金额表示净往来或利润。

### 4.2 主要指标口径

- 项目数：当前权限范围内至少有一个正式关联的去重项目。
- 主合同当前金额：关联项目当前有效合同金额。
- 分供合同当前金额：原签约金额加有效补充协议净额，按状态口径区分终止合同。
- 累计结算额：已过账结算的本次增减额合计/最终累计快照；最终累计金额只过账差额。
- 应付未付：已过账正向应付减有效付款核销净额；供应商负向结算形成的待返还/抵扣另行显示，当前没有自动跨应付抵扣流程。
- 净付款：付款流水减退款流水。
- 发票：发票金额、已核验发票金额单独统计，不当作已付或已计成本。
- 实际成本：合同关联成本与独立成本分开展示，成本归集不因付款或开票自动发生。

单位经营档案的独立成本摘要可计算全量聚合；为了控制响应体大小，明细列表仅展示最新 200 条，并提示用户这是最近明细而非全部记录。

## 5. 迁移与历史数据

迁移 `20261014020000_business_party_master` 为新增迁移，不修改历史迁移。新增 `BusinessParty`、枚举、关联外键与索引，保留旧名称文本字段。旧数据按规范化名称聚合生成身份未核验的暂存单位并回填 ID，身份核验备注提示需要复核。

这一步是数据迁移辅助，不是法律身份已验证。如果旧名称相同但实际上对应不同总分公司、地区分支、项目部或独立法人，必须在正式对账前人工复核和修正关联。部署前备份数据库；先在数据库副本上迁移，抽查同名、多角色、空名称、非标准空格、分支机构等数据。

## 6. 权限和审计

- 公司 ADMIN 可浏览全公司范围、创建同名不同主体档案、维护统一主档并核验身份。
- 有相应项目业务权限的用户可以新建单位档案，并在自己有权限的合同/项目里关联。
- 普通用户可查询单位基础识别信息，但不应获得不相关项目的项目名称、合同金额、结算、应付、付款、银行或发票信息。
- 单位详情接口必须在数据库查询层按 `ProjectMember` 过滤，而不是只在前端隐藏结果。
- 公司级名称、角色、信用代码、状态和身份核验变更都记录审计；不直接删除仍被业务单据引用的单位，优先停用/归档。
- 单位主档中的银行账户和多个联系人维护尚未在本版单独建模，后续应独立加权限控制；当前档案包含基础联系方式和开票资料，普通单位列表只返回合同录入所需的基础联系方式/开票识别信息，不返回档案备注、核验依据等全部字段。

## 7. 当前边界

本候选版本没有提供复杂的批量合并/拆分工作台，也没有自动跨应付抵扣、完整主合同竣工结算/应收账款或会计总账。历史关联是按名称回填并明确未核验的过渡状态。正式上线前应补做管理员身份复核和异常关系整改，并在 Node.js 24+ 环境完成 Prisma、PostgreSQL 迁移、完整类型检查、构建和 Windows 端到端验收。
