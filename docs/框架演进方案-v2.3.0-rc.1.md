# 墨衡框架演进与 PostgreSQL 后台任务队列 v2.3.0-rc.1

- 基线：`v2.2.0-rc.1`
- 候选版本：`v2.3.0-rc.1`
- 日期：2026-10-15
- 原则：增量演进；保留既有合同、变更签证、结算、应收应付、收退款和审计业务语义；数据库改动只通过新增迁移完成。
- 发布状态：Release Candidate。源码已增量修改，但完整构建、数据库迁移和实机端到端结果需以单独验收记录为准。

## 1. 决策摘要

继续采用 **React + TypeScript + Fastify + PostgreSQL + Prisma 的模块化单体**。本轮增加一个使用现有 PostgreSQL 的轻量任务队列，用于原生 XLSX 报表导出；默认不引入 Redis、RabbitMQ、Kafka、独立对象存储或 Kubernetes。

| 决策 | 当前做法 | 未来扩展时的稳定边界 |
|---|---|---|
| 正式业务数据 | PostgreSQL 是事实源 | 缓存/消息系统不得变成合同金额、应收应付或资金余额的权威来源 |
| HTTP/API | Fastify 路由插件 + OpenAPI | 兼容现有 `/api` 契约；破坏性变更走显式 API 主版本 |
| 业务规则 | 现有领域数学、状态机和事务继续留在后端 | 外部系统只调用应用用例或订阅已生效事件，不复制计价/过账规则 |
| 后台任务 | `BackgroundJob` + PostgreSQL worker | `type`、`payloadVersion`、handler 注册表构成任务契约；可以将 worker 从 API 进程拆出 |
| 事务后副作用 | 在业务事务内插入待处理任务 | 后续通知/财务同步可采用 Transactional Outbox 模式，通过同一事务写事件任务，避免“业务提交成功但通知未入队” |
| 外部系统 | 通过标准化 API/适配器接入 | 供应商 SDK、凭据、重试和协议转换封装在 adapter，不进入核心财务逻辑 |
| 文件 | 当前保存在服务端受控目录 | 由 `backgroundJobArtifactPath()`/存储适配层隔离路径；将来可替换为 S3/OSS，不向业务模块暴露物理路径 |

## 2. 逻辑架构

```text
浏览器 / 移动端 / 外部系统
       │ HTTPS + REST + OpenAPI
       ▼
Fastify 模块化单体
  ├─ 认证、项目访问控制、API 契约
  ├─ 合同、变更、结算、收付款、目标成本等现有业务
  ├─ 报表/模板 API（同步 CSV + 异步 XLSX）
  └─ 后台任务生产者
       │ Prisma / PostgreSQL transaction
       ├──────────────► 正式业务表（业务事实源）
       └──────────────► BackgroundJob（队列表）
                              │ FOR UPDATE SKIP LOCKED
                              ▼
                       Background Worker
                              │ type + payloadVersion
                              ▼
                       Handler Registry
                        ├─ report.xlsx.export
                        └─ future integration.* handlers
                              │
                              ▼
                       文件 / 外部服务适配器（按需）
```

逻辑层并不等于独立部署服务。当前 Windows 默认模式下，API 与 worker 在同一 Node.js 进程运行；容器部署可以默认采用相同模式。需要将 CPU/内存负载隔离时，可关掉内置 worker 并单独启动 `dist/src/worker.js`，多个 worker 仍通过数据库锁安全竞争任务。

## 3. PostgreSQL 任务队列契约

### 3.1 `BackgroundJob` 字段语义

- `type`：稳定任务名，例如 `report.xlsx.export`。禁止使用文件路径、类名或供应商 SDK 名作为长期契约。
- `payloadVersion`：参数结构版本；handler 必须校验版本。破坏性 payload 变更要增加版本并保留必要的兼容解析。
- `payload`：仅保存 JSON 参数和稳定业务 ID；不能存 JWT、Cookie、密码或完整密钥。
- `ownerUserId` / `projectId`：用于状态查询、结果下载和授权复核。
- `idempotencyKey` + `requestHash`：防止同一账号以相同幂等键提交不同参数；数据库唯一约束为 `(ownerUserId, idempotencyKey)`。
- `attempts` / `maxAttempts` / `availableAt`：限制重试次数并用指数退避延后下一次尝试。
- `lockedAt` / `lockedBy`：任务租约。worker 崩溃后，过期租约可由其他 worker 重新领取。
- `resultFileName` / `resultExpiresAt`：只存服务端生成的文件名，不保存客户端路径；导出文件保存 7 天，终态任务记录在清理条件满足后可删除。
- `lastError`：仅作为运维诊断摘要，不在普通用户接口中泄露原始异常或内部路径。

### 3.2 状态机

```text
QUEUED ──领取──► RUNNING ──成功──► SUCCEEDED
   ▲                 │
   │                 ├──可重试失败且次数未尽──► QUEUED（退避后）
   │                 └──不可重试/次数耗尽────► FAILED
   └────── RUNNING 租约过期且仍可重试 ───────┘
```

`CANCELLED` 已预留为状态值，本候选不提供用户取消接口；不得据此宣称具备取消正在运行任务的能力。

### 3.3 并发与故障处理

1. `claimNextBackgroundJob()` 在数据库事务内用 `FOR UPDATE SKIP LOCKED` 选择并更新一条任务，支持多个 worker 并发领取。
2. worker 心跳更新租约；worker 崩溃后，超过租约的任务可由其他 worker 接管。
3. handler 需要区分可重试的暂时故障与 `PermanentBackgroundJobError`。重试有次数上限和退避时间，不无限循环。
4. 任务可能由于租约恢复而被再次执行。**任务执行必须可重复**：导出文件用任务 ID 与尝试次数共同生成唯一文件名，避免过期 worker 覆盖较新尝试；未来外部写入必须使用外部幂等键/投递 ID。
5. 任务入队可以在业务事务内通过 `enqueueBackgroundJob(tx, ...)` 完成；如果业务变更与副作用必须原子关联，应在同一事务写入相应事件任务（Transactional Outbox 模式），不能先提交业务再直接调用外部 HTTP。
6. worker 内部状态不应由浏览器直接写入；只通过受控接口提交、查询或下载任务。

### 3.4 当前 API

| 方法 | 路径 | 用途 |
|---|---|---|
| `POST` | `/api/reports/:reportKey.xlsx/jobs` | 提交异步 XLSX 导出，支持 `Idempotency-Key` 请求头 |
| `GET` | `/api/reports/jobs/:jobId` | 查询任务状态和结果可用性 |
| `GET` | `/api/reports/jobs/:jobId/download` | 下载成功且未过期的文件 |
| `GET` | `/api/reports/:reportKey.xlsx` | 保留原同步导出接口，确保现有集成不被破坏 |
| `GET` | `/api/reports/:reportKey.csv` | 继续提供同步 CSV 导出 |

每个接口均需要认证。状态/下载接口检查任务所属用户（管理员例外）并重新检查项目权限；执行 handler 时再次验证用户仍启用、项目仍可访问，以及使用的模板仍可读取。文件名和输出路径由服务端控制。

## 4. 未来外部服务不侵入核心业务的规则

新增通知、电子签章、财务/ERP、电子发票、对象存储或 AI 服务时，依序按以下边界实现：

1. **领域动作先完成其自身业务校验。** 内部审批与外部确认分离、有效合同额生效条件、结算过账及退款冲销规则仍由墨衡决定。外部服务的回调不得直接改写金额字段。
2. **HTTP 层只做请求适配。** 解析输入、授权、调用应用用例、返回稳定错误码；外部供应商 SDK 不允许散布到业务路由中。
3. **需要异步的副作用转为明确任务类型。** 用 `enqueueBackgroundJob(tx, ...)` 与关键业务事务一起提交，或通过领域事件/发件箱服务在同一事务中写待发送事件。
4. **handler 依赖 adapter 接口。** 如 `NotificationAdapter.send()`、`FinanceAdapter.pushChange()`、`FileStorageAdapter.put/get()`；凭据、HTTP 格式、供应商限流和重试归 adapter/worker 管理。
5. **事件和任务契约稳定且版本化。** 事件至少含 `eventId`、`eventType`、`schemaVersion`、`occurredAt`、聚合根 ID 与必要业务字段；不包含令牌、原始凭证文件路径或多余个人信息。
6. **外部调用至少一次语义。** 重试通常会带来重复投递，因此消费者必须根据 `eventId` 或业务幂等键去重。除非下游明确支持且经过验证，不承诺端到端 exactly-once。
7. **供应商替换不改财务状态机。** 更换微信/邮件、云存储、签章平台或 AI 模型，只更换适配器配置和实现，不更改合同/结算领域规则。

## 5. 什么情况下才新增 Redis、RabbitMQ 或 Kafka

- **Redis：** 有真实的重复读瓶颈、跨实例缓存/限流/协调问题，并能定义缓存失效与不可用回退时再加；正式财务数据仍以 PostgreSQL 为准。
- **RabbitMQ：** 需要与主应用隔离的任务分发、复杂路由、独立消费者扩缩容或更成熟的确认/死信流程时再评估。
- **Kafka：** 多个独立系统需要高吞吐事件流、事件保留与消费位置管理、历史重放或实时数据管道时再评估。
- **不升级的判断依据：** 当前队列平均/峰值积压、任务时延、数据库负载、重试率、部署资源和运维能力均应有实测数据。单纯“行业常用”不是新增依赖理由。

## 6. 部署与配置

Windows 原生默认：

- `BACKGROUND_WORKER_ENABLED=true`：由 API 进程内启动 worker，新增服务数量为零。
- `BACKGROUND_JOB_POLL_MS=1000`：空队列轮询间隔，可配置 250–60000 毫秒。
- `BACKGROUND_JOB_STORAGE_DIR`：默认 `<apps/api 当前工作目录>/data/jobs`。该目录必须位于静态资源根目录之外，并配置仅服务账号可访问的 NTFS ACL；纳入独立于数据库的备份/清理策略。

需要独立进程时：先设置 API 的 `BACKGROUND_WORKER_ENABLED=false`，完成构建和迁移后再单独运行 `npm run worker -w @cms/api`，并通过 Windows 任务计划程序或服务管理器维护该进程。不要在未确认共享存储路径的情况下运行两个指向不同目录的 worker。

Docker Compose 默认仍由 API 进程内执行 worker，job 文件保存在 `job-data` named volume。如果要启用独立 worker profile：在项目根 `.env` 中设置 `BACKGROUND_WORKER_ENABLED=false`，随后运行 `docker compose --profile worker up -d`；worker 与 API 必须挂载同一个 `job-data` volume。不要同时把文件目录放在容器临时层。

新迁移：`20261015020000_postgresql_background_jobs`。生产环境必须在备份副本上执行迁移，并在运行 API/worker 前生成匹配的 Prisma Client。

## 7. 发布 Gate

- **Gate A — 静态契约：** Prisma schema/迁移字段一致、无强制 broker/cache 依赖、队列领取使用 `SKIP LOCKED`、幂等/租约/重试/结果清理检查通过。
- **Gate B — 干净构建：** Node.js 24+ 环境执行 `npm ci`、`npm run db:generate`、严格 API/Web TypeScript 检查、lint、生产构建及单元测试。必须提交经过审查的锁文件。
- **Gate C — 数据库：** PostgreSQL 16 测试副本上执行迁移；验证多 worker 并发无重复领取、进程崩溃租约恢复、重试上限、重复 Idempotency-Key、权限撤销后的任务执行/下载、过期文件清理与备份恢复。
- **Gate D — 浏览器/Excel：** 报表中心提交任务、轮询、超时提示和下载验证；检查真实 Excel/WPS 打开、多工作表/打印设置及 10,000 行限制。
- **Gate E — 财务回归：** 业主/分供合同生效金额、阶段/最终结算差额、应收应付、收退款冲销和审计快照与基线完全一致。

静态契约通过不等于 Gate B–E 通过。任何一个 Gate 尚未执行时，版本均保留 `rc` 标记。
