# 未迁移项登记

这些规则地图判定为"可删"，但实测或阅读后确认不该删。记在这里，避免下次重复排查。

## 1. `@media print` 块（v6.css:1092-1096）

```css
@media print{
  .sidebar,.topbar,.project-context-bar,.app-footer,.cost-workspace-tabs,.system-workspace-nav{display:none}
  .main-shell{margin:0}
  body{background:#fff}
}
```

**为什么不删**：hana.css 里**没有任何 `@media print` 规则**。地图只比对 `display` 属性名在别处是否声明，看不见"这是唯一一条打印样式"。

删掉后打印页面会印出侧栏、顶栏、页脚和成本工作台标签。

**为什么难验证**：打印媒质无法用截图或计算样式快照覆盖。Chrome DevTools 的 `emulateMediaType('print')` 可以测，但截图工具链不经过这条路径。

## 2. `.select-control-chevron`（legacy.css:1492）

```css
.select-control-chevron { flex: 0 0 auto; color: var(--text-muted); transition: transform .2s var(--ease-spring), color .2s ease; }
```

**为什么不删**：地图报 `declCount: 1, fully: ["color"]`——只统计外观白名单内的属性。`flex` 和 `transition` 不在白名单，地图看不见。

hana.css 里 `.select-control-chevron` 出现 **0 次**。删掉后下拉箭头的旋转动画消失。

## 3. `.date-picker-*` 三兄弟

- `.date-picker-proxy`（legacy:1520）：带 `pointer-events: none`，隐藏原生日期输入但保留其能力
- `.date-picker-value`（legacy:1522）：带 `flex: 1`，是布局而非外观
- `.date-picker-icon`（legacy:1524）：带 `transition`，图标动画

同 2：外观属性被覆盖，但行为属性没有。

## 4. `.status-badge`（v6.css:212）

hana.css 缺 `height` 和 `letter-spacing`，地图判为 partial 而非 dead。记录在此仅为说明它为何仍在。

## 5. `.panel-heading p` 的布局属性（已处理）

原规则同时声明排版和布局：

```css
.panel-heading p { display: flex; align-items: center; gap: 5px; margin: 4px 0 0; color: var(--meta); font-size: 10px; }
```

hana.css 只接管了排版（`margin`/`color`/`font-size`）。处理方式是**保留布局三属性、删除已接管的排版属性**，不是整条删也不是整条留。

这开创了一个模式：**混合属性规则只摘掉被接管的部分**。

## 判据小结

地图的"可删"意味着：**该规则声明的每个外观属性，都有别处也在声明**。

它**不**意味着：

- 该规则的其他属性（布局、动效、交互）也被接管
- 媒体查询的语境被考虑
- 这条是唯一一条满足某条件（如打印）的规则

所以每次批量删除后必须实测，实测必须覆盖：

| 手段 | 能发现什么 |
| --- | --- |
| 单视口计算样式快照 | 视觉属性变化 |
| 四视口快照 | 断点内规则失效 |
| 焦点探针（真实 Tab） | `:focus-visible` 相关 |
| 人工读原文 | 行为属性（transition/flex/pointer-events）|
| 印刷媒质 | **目前无法覆盖，只能靠人工判断** |

# 附：与 hana 形态对齐时，主动不改的项

下面这些是「与 hana 写法不同，但 moheng 的写法更正确」的情况。**不要因为对比出差异就改。**

## 6. 顶栏 `padding-left: 24px`（保持 24，不改成 hana 的 12）

hana `.titlebar` 是 `padding: 0 var(--space-12)`（左右都 12）。
moheng `.app-titlebar` 是 `padding: 0 var(--space-12) 0 var(--space-24)`（左 24 / 右 12）。

看似不对称是个疏漏，实测却发现它是**算过的**：

| 视口 | 面包屑左缘 | 下方内容块左缘 | 差值 |
| --- | --- | --- | --- |
| 1440px | 270 | 274 | **4px** |
| 1024px | 270 | 266 | **4px** |

两个视口都稳定 4px。改成 12px 后差值变成 16px / 8px，顶栏文字与内容明显错位。

**原因**：hana 的顶栏跨整个窗口（侧栏在它下方），左边没有东西要对齐。
moheng 的顶栏在侧栏右侧，需要和下方 `.page-wrap` 的左边距对齐。

## 7. 侧栏脚 `display: block`（保持 block，不改成 hana 的 flex）

hana `.sidebar-footer` 是 `display:flex; gap:var(--space-2)`。moheng 是 `display:block`。

实测 moheng 的脚只有 **1 个子元素** `.sidebar-user-row`，它本身已经是 flex。

`gap` 在单子元素容器里永不生效，改 flex 是纯形式对齐，零收益且有布局风险。

**原因**：hana 的脚里是一排图标按钮（需要 gap 排布），moheng 的脚里是一个用户信息行，**形状不同**。

## 教训："与 hana 不同" ≠ "需要改"

这两项的共性是：差异存在，但差异背后是 moheng 的真实约束（内容宽度对齐、子元素数量）。

对齐 hana 之前先问：**hana 那个写法是为了解决 moheng 也面临的问题吗？**
如果不是，差异就是合理的。
