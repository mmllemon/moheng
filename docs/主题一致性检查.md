# 主题一致性检查（2026-10-22）

## 为什么做这个

前面所有迁移验证都在**单一主题（warm-paper）**下跑「零差异」。

但这次改造的核心价值是把硬编码色换成 token——**这个价值在单主题下完全体现不出来**，因为硬编码的颜色恰好等于当前主题的 token 值。

输入控件那次就是活证据：`#fffdf7` 碰巧约等于 `--bg-card`，所以「看起来正常」了很久。

所以补了主题维度的验证。

## 结论：主题跟随是健康的

### 1. 硬编码颜色分布

| 文件 | hex | rgb | 合计 |
| --- | --- | --- | --- |
| **hana.css**（目标层） | 13 | 21 | **34** |
| legacy.css | 307 | 72 | **379** |
| v6.css | 56 | 51 | **107** |

目标层 hana.css 本身只有 34 处硬编码，很干净。旧层的 486 处正是要清的对象。

### 2. 表面元素跟随情况

在 4 套主题（warm-paper / plain-white / midnight / high-contrast）下分别采集：

| 表面 | 背景色种类 | 判定 |
| --- | --- | --- |
| `body` | 4 | ✓ 完全跟随 |
| `.panel` | 4 | ✓ 完全跟随 |
| `.data-table thead th` | 4 | ✓ 完全跟随 |
| `.data-table tbody td` | 4 | ✓ 完全跟随 |
| `.button-secondary` | 4 | ✓ 完全跟随 |
| `.status-badge` | 4 | ✓ 完全跟随 |
| `.page-header` | 4 | ✓ 完全跟随 |
| `.button-primary` | 3 | ✓ warm-paper 与 plain-white 共用同一 accent |
| `h1` / `.metric` / `input` | 1（均为透明） | ✓ 继承父级，非硬编码 |

### 3. 语义色跟随情况

| 主题 | 绿色（已结算） | 蓝色（施工中） | 橙色（未启用 MFA） |
| --- | --- | --- | --- |
| warm-paper | `rgb(74,107,74)` | `rgb(70,107,128)` | `rgb(138,95,26)` |
| plain-white | 同上 | 同上 | 同上 |
| **midnight** | `rgb(168,221,170)` | `rgb(230,177,196)` | `rgb(230,200,136)` |
| high-contrast | `oklch(0.28 0.012 250)` | `rgb(44,90,81)` | 同上 |

深色下绿色从亮度 107 提到 221、橙色从 95 提到 200——正是浅色底调整深色时该做的补偿。

**说明 `--status-*` 这类语义 token 已经在正常工作。**

### 4. 一个容易误判的点

初版探针用「深色主题下背景仍是浅色 = 硬编码」做判据，报了 `.button-primary` 在 midnight 下是 `rgb(230,177,196)`。

查来源发现这是 hana.css 第 214 行 `--accent: #e6b1c4`——**midnight 主题主动把主色调成粉色**，不是 bug。

判据应改为「相对比较」：同元素在各主题间是否真的变了，而不是预设立场判断深浅。

## 遗留项

`legacy.css` 里 379 处硬编码中，约 57 处「命中「某主题 token 的值」——但绝大多数是 `#fff` 恰好等于 plain-white 的 `--bg-card`，属于巧合匹配而非隐患。

真正需要关注的是**带透明度的白色**（`rgba(255,255,255,.055)` 这类），它们假设了深色背景。目前用于 `.sidebar` 内部，而 `.sidebar` 在 4 个主题下都保持深色，所以没问题。

如果将来要让 sidebar 也跟随主题明暗，这批才会出问题。
