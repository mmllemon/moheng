# 开发维护指南

- 产品：墨衡｜施工单位成本管理系统
- 版本：MVP 1.6.0-rc.1 验证候选（Windows 原生部署优先）
- 设计依据：《施工单位成本管理系统完整设计方案 v1.0》（2026-10-12）
- 适用对象：开发人员、数据库管理员、部署与运维人员

## 1. 系统范围与运行形态

系统服务于施工阶段收入与成本台账。当前已实现：

1. 登录、JWT access token、HttpOnly refresh cookie 及会话续期。
2. 项目新增、编辑、列表过滤和项目上下文切换。
3. 主合同信息维护。
4. 目标成本清单、层级显示及 CSV 导入。
5. 人工、材料、机械、分包和间接成本录入与软归档。
6. 进度款申报状态流转、核定额和分次到账。
7. 业主主合同与进度款/变更签证建立关联，历史未关联记录在主合同保存时自动补关联并记审计。
8. 分供合同台账、追加式有效补充协议、付款计划、实付/退款现金流台账。
9. 分供阶段/最终结算、可选结算明细、外部确认与过账、应付单、付款核销、预付款扣回、质保金及供应商发票核验。
10. 实际成本新增时可关联合同，历史成本可人工补关联；结算/发票/付款与实际成本分开归集，避免双计。
11. 变更签证内部状态与外部确认状态分离；A/B/C 凭证登记、C 类独立核验和凭证本地存储。
12. 原始合同金额与当前有效合同额分开保存；有效合同额由已生效外部确认调整净额重算。
13. 系统账号创建、项目成员角色分配及关键动作审计。
15. 往来单位主数据、单位经营档案与跨项目聚合。
16. 业主侧竣工结算、应收账款、到账/退款核销、预付款和质保金释放。
17. 数据库序列生成业务编号、记住账号与浏览器密码管理器兼容。
18. 分供合同付款与分供结算应付共享工作台入口，并将项目工作台导航分为收入侧和成本支出侧。
14. 经营仪表盘、月度成本图表与三算分析。

以下模块尚未实现：材料入库/验收及退货、完整发票/验收/结算三单匹配、供应商负向调整的自动跨应付抵扣流程、跨应收单自动抵销工作流、会计总账凭证/税务处理、未开票应计成本核销、材料库存及历史价格、其他业务单据的对象存储附件、XLSX 导入映射、Excel/PDF 异步报表、通知推送、PWA 离线同步与冲突解决、公司级可配置审批链、密码重置/停用等完整用户生命周期。变更凭证附件当前只采用本地受控存储，尚未包含病毒扫描或对象存储。未实现功能不可通过手工写入数据库或默认数据推断为已交付。

### 1.1 生产部署架构

```text
Browser
  │ HTTP / HTTPS
  ▼
Fastify API（同源提供 React dist + REST API + OpenAPI UI）
  │ Prisma Client
  ▼
PostgreSQL 16（项目数据、业务审计、刷新令牌哈希）
```

Windows 原生部署不需要 Redis、Docker Desktop 或 Nginx。Node.js 负责服务端运行与静态文件托管，PostgreSQL 作为 Windows 服务运行。若需要局域网或公网访问，应在 IIS/企业反向代理配置 HTTPS、访问控制和必要的请求日志，不建议直接暴露 Node 监听端口。

Docker Compose 仍保留为可选方案：PostgreSQL + API + Nginx Web。它同样不依赖 Redis。

## 4. Windows 原生部署

### 4.1 前置条件

- Windows 10/11 或 Windows Server（建议使用仍受组织安全更新支持的版本）。
- Node.js 24 LTS、npm。
- PostgreSQL 16 或更高兼容版本，并作为自动启动的 Windows 服务运行。
- PowerShell 5.1 或 PowerShell 7。
- Prisma 在 Windows 上可能需要 Microsoft Visual C++ Redistributable 2015 或更高版本。
- 安装依赖时必须能访问 npm registry；离线环境需事先缓存/镜像依赖和安装包。

### 4.2 PostgreSQL 初始化

通过 pgAdmin 或 `psql` 用数据库管理员账号创建应用角色与数据库：

```sql
CREATE ROLE cms_user LOGIN PASSWORD '使用URL安全字符的强密码';
CREATE DATABASE cost_management OWNER cms_user;
```

若角色或数据库已经存在，请按现场环境核对而不是重复执行。应用角色只应拥有业务数据库需要的权限，不应使用 PostgreSQL 超级用户作为运行账号。

### 4.3 配置环境变量

复制模板并编辑：

```powershell
Copy-Item apps/api/.env.example apps/api/.env
notepad apps/api/.env
```

| 变量 | 作用 | 原生部署建议 |
|---|---|---|
| `NODE_ENV` | 运行环境 | `production` |
| `PORT` | HTTP 监听端口 | 默认 `3001` |
| `HOST` | 监听地址 | 默认 `127.0.0.1`；仅在有防火墙/代理策略时改成 `0.0.0.0` |
| `DATABASE_URL` | PostgreSQL 连接 | 指向本机或内网 PostgreSQL；用户名、密码、数据库要一致 |
| `JWT_SECRET` | JWT 签名密钥 | 至少 32 字符的随机值，严禁使用示例密钥 |
| `COOKIE_SECURE` | 刷新 Cookie 的 Secure 标志 | HTTPS 环境必须为 `true`；仅本机 HTTP 测试可以 `false` |
| `CORS_ORIGIN` | 允许跨源访问的前端来源 | 只列实际可信 Origin；生产同源部署不需要额外开放来源 |
| `EVIDENCE_STORAGE_DIR` | 变更凭证文件本地目录 | 使用专用、限制访问、可备份的持久化目录；默认 `apps/api/data/evidence`。Windows 上必须另行设置 NTFS ACL，仅允许 API 运行账号和备份管理员访问，不能把 POSIX 文件模式 `0600` 当成 Windows ACL |
| `SEED_ADMIN_NAME` | 初始管理员姓名 | 按组织要求设置 |
| `SEED_ADMIN_EMAIL` | 初始管理员邮箱 | 必须是可唯一识别的账号 |
| `SEED_ADMIN_PASSWORD` | 初始管理员密码 | 设置强密码；种子脚本不会覆盖已有管理员的密码 |
| `SEED_DEMO_DATA` | 是否创建演示项目 | 生产默认 `false` |

建议数据库密码仅使用字母、数字、下划线和短横线，以避免 `DATABASE_URL` 中特殊字符编码问题。不要把 `apps/api/.env` 放入源代码管理，也不要把它发给普通业务用户。

### 4.4 构建、迁移及初始化

```powershell
Set-ExecutionPolicy -Scope Process Bypass
.\scripts\windows\prepare-windows.ps1
```

脚本执行 Node.js 检查、`npm install`、Prisma Client 生成、前后端构建、`prisma migrate deploy` 和种子数据。若 `.env` 不存在，脚本会复制示例文件并以代码 2 退出；编辑文件后重跑。若要跳过迁移或种子，可以传 `-SkipDatabaseMigration`、`-SkipSeed`，但只有在数据库状态已有明确管理流程时才应跳过。

常规启动：

```powershell
.\scripts\windows\start-windows.ps1
Invoke-RestMethod http://localhost:3001/health
```

系统：`http://localhost:3001`；API 文档：`http://localhost:3001/docs/`。停止：

```powershell
.\scripts\windows\stop-windows.ps1
```

进程日志位于 `apps/api/logs/api.out.log` 与 `apps/api/logs/api.err.log`。

### 4.5 开机自动启动

用管理员身份打开 PowerShell：

```powershell
.\scripts\windows\register-startup-task.ps1
```

脚本注册 `ZhuhengCostManagement` 任务，由 SYSTEM 在系统启动时运行 `scripts/windows/run-api.ps1`。任务运行器将进程输出追加到 `apps/api/logs/api-service.log`，并配置失败后最多重启 5 次。若项目放在普通用户专属目录、网络盘或加密盘，应先确保 SYSTEM 能读取 `.env`、Node.js、`dist`、`node_modules` 和日志路径。推荐把部署目录放在受控的本地磁盘路径，例如 `C:\Apps\Zhuheng`，并只给管理员和服务运行身份必要权限。

卸载任务：

```powershell
.\scripts\windows\unregister-startup-task.ps1
```

任务计划程序不负责自动安装数据库，也不替代数据库备份。应设置 PostgreSQL 服务为自动启动，验证数据库启动早于应用访问，并在实机重启演练中检查失败重启策略与日志。

### 4.6 开发模式

`apps/api/.env` 配置好 PostgreSQL 后，在项目根目录执行：

```powershell
npm install
npm run db:generate
npm run db:deploy
npm run db:seed
npm run dev
```

Vite 地址为 `http://localhost:5173`，Fastify 为 `http://localhost:3001`。生产模式下前端构建输出位于 `apps/web/dist`，Fastify 从同源提供页面、`/assets/*` 和 `/api/*`，避免跨源部署带来的额外配置。Vite 开发服务器会把 `/api` 代理至 3001 端口。

## 5. 可选 Docker 部署

根目录 `.env.example` 用于 Docker Compose，不是 Windows 原生 API 的唯一配置。Docker 部署步骤：


## 6. 认证及安全模型

### 6.1 登录与刷新令牌

- 登录成功签发有效期 15 分钟的 JWT access token。
- 系统生成 48 字节随机 refresh token，仅把其 SHA-256 哈希写入 `RefreshToken` 表。
- 原始 refresh token 仅通过 `HttpOnly` Cookie 返回，Cookie Path 为 `/api/auth`，生命周期 7 天。
- `/api/auth/refresh` 使用一条 `DELETE ... RETURNING` SQL 原子删除仍有效的旧哈希并取回用户 ID，旧 token 无法被并发重复消费。
- 成功后签发新 refresh token；注销时删除当前哈希并清除 Cookie。
- 已过期哈希会在签发新 token 时顺带清理；生产规模增长后可以增加周期清理任务。

### 6.2 项目权限

- 全局 `ADMIN` 可跨项目访问并维护系统账号。
- 普通用户仅能访问存在 `ProjectMember` 关系的项目。
- `OWNER` / `MANAGER` / `ESTIMATOR` 可执行当前已开放的项目写入操作；内部核定和 C 类凭证核验限制 `OWNER` / `MANAGER`。
- `VIEWER` 只读。
- 系统管理员可在“账号与项目权限”页创建普通用户并分配项目角色；项目负责人/经理也可通过受限 API 分配其授权范围内的较低角色。角色分配和用户创建写入 `AuditLog`。
- 用户创建默认不能设为全局 `ADMIN`，防止普通账号自我提权。

### 6.3 金额与审计边界

金额字段在 PostgreSQL 使用 `DECIMAL`；合同有效额的重算在服务端以整数分累加，且用事务与项目行锁串行化重算。原始合同额保存在 `Project.originalContractAmount`，`Project.contractAmount` 作为当前有效合同额缓存，等于原始合同额加上所有有效外部确认调整的有符号净额。所有凭证登记、核验、生效与下载动作写入 `AuditLog`；同一项目内按确认人、授权、时间、金额、范围和凭证定位构成确认指纹，并串行化检查重复登记。API 仍将部分金额序列化为 JSON 数值，正式财务对账仍应以数据库 Decimal 为准；含税/不含税、税额、舍入和冲销流程需在正式上线前进一步明确。

### 6.4 下游合同、承诺、成本与付款口径

- `DownstreamContract.originalAmount` 是已签合同的原始基准；状态激活后锁定。当前合同额 = 原始金额 + `DownstreamContractAdjustment` 中已登记的有效补充协议增减净额。补充协议采用追加记录，禁止原位覆盖基准。
- `DownstreamContract.status=ACTIVE` 或 `COMPLETED` 时，合同当前金额纳入“执行中/完工待结算合同额”汇总；`DRAFT`、`SETTLED`、`TERMINATED` 不纳入该汇总。此指标只是执行中/完工待结算合同当前金额合计，不是剩余履约义务或已承诺未履约金额的精确计量。
- `DownstreamPaymentPlan` 是预计现金流计划，不表示付款已经发生，不计入实际成本。
- `DownstreamContractPayment` 记录实际现金流。普通付款金额以正数登记；`REFUND` 也以正数保存，但从累计净付款中扣减。退款不可超过合同/所选计划当前净已付款。相同合同内的非空银行流水/参考号唯一；每次付款/退款保留独立审计，不覆盖历史付款。
- `CostEntry.downstreamContractId` 是可选的成本来源关联。只有成本录入记录计入实际成本；付款记录不会自动创建或冲减成本；退款必须引用同一合同下的原始非退款付款，累计退款不能超过原始付款金额，并自动继承该笔付款的付款计划。历史成本默认不自动匹配合同，需要经办人员根据合同、发票、验收或结算依据手工补关联。
- `contractValueMinusLinkedActualCost = max(合同当前金额 - 已关联实际成本, 0)` 以及 `linkedActualCostOverContractValue` 只是快速预警值。履约/验收计量、未开票应计成本、税差与索赔尚未完整建模；虽然本版本已有结算和质保金台账，但还不是完整会计/成本过账模型，不能将该估算等同于专业“未履约承诺”或预计完工成本。
- `ProgressBill.mainContractId` 和 `Change.mainContractId` 将业主进度款/变更签证绑定到主合同；项目维度用于归集和访问控制。每个项目目前仅允许一份 `MainContract`。历史未关联收入记录在主合同保存时只补齐空关联，不搬动已有非空关联，并写入审计日志。

## 7. 数据库设计摘要

Schema：`apps/api/prisma/schema.prisma`。

| 模型 | 用途 | 主要约束 |
|---|---|---|
| `User` | 用户 | 邮箱唯一，密码为 bcrypt 哈希 |
| `RefreshToken` | 刷新会话哈希 | 哈希唯一，含过期时间，用户删除时级联删除 |
| `Project` | 项目档案 | 项目编号唯一，支持软删除 |
| `ProjectMember` | 项目角色 | `(projectId,userId)` 唯一 |
| `MainContract` | 主合同 | 每项目最多一条主合同 |
| `BudgetItem` | 树形目标成本清单 | 项目内编号唯一，支持软删除 |
| `CostEntry` | 实际成本 | `Decimal(18,2)` 金额，可选关联同项目下游合同，支持软删除 |
| `DownstreamContract` | 分供合同（数据库模型名保持兼容） | 项目内合同编号唯一，原始金额激活后不可覆盖 |
| `DownstreamContractAdjustment` | 对下已生效补充协议 | 追加记录，合同内协议编号唯一 |
| `DownstreamPaymentPlan` | 对下预计付款计划 | 累计计划金额不得超过当前合同额 |
| `DownstreamContractPayment` | 分供实际付款/退款 | 合同内非空参考号唯一；退款须关联原始付款并继承对应付款计划，独立留痕并从净付款扣减 |

### 7.1 三算分析的当前口径

- 合同金额：使用 `Project.contractAmount` 当前有效合同额，并单独保留 `Project.originalContractAmount`；主合同录入的 `amount` 是基准金额。
- 目标成本：合计叶子清单项，避免父项、子项重复相加。
- 实际成本：统计未软归档的成本记录。
- 预计完工成本：目标成本存在时用目标成本作简化基线，否则回退到实际成本；不含基于剩余工程量、未录入承诺成本或挣值预测的计算。
- 有效变更净额是外部确认状态为 `EFFECTIVE` 的调整按增加/减少方向求和；有效合同额更新会反映到总览和成本分析，内部审批金额本身不改变有效合同额。
- 收款金额以进度款到账明细为依据；申报状态和实际到账是分开的。

### 8.1 主要状态机

进度款：

```text
DRAFT → SUBMITTED → UNDER_REVIEW → APPROVED →（到账完成后）PAID
                      └────────→ REJECTED → DRAFT
SUBMITTED ─────────────────────→ REJECTED
```

变更签证的公司内部状态仍采用固定状态流（尚未实现公司级可配置审批链）：

```text
DRAFT → SUBMITTED → UNDER_REVIEW → CONFIRMED（内部审批已完成）
                      └────────→ REJECTED
SUBMITTED ─────────────────────→ REJECTED
```

外部确认是独立状态流，不与内部 `CONFIRMED` 混同：

```text
NOT_CONFIRMED → EFFECTIVE（A/B 且材料齐备）
NOT_CONFIRMED → PENDING_VERIFICATION（C 类）→ EFFECTIVE / REJECTED / DISPUTED
NOT_CONFIRMED → PENDING_SUPPLEMENT（补充材料后可再次登记）
```

只有 `externalConfirmationStatus=EFFECTIVE` 的外部确认金额参加有效合同额计算。核验 C 类凭证时，提交人（`submittedById`；旧数据回退检查 `createdById`）不得成为核验人。已生效凭证不允许原位覆盖；有争议或需更正时必须保留原纪录并按更正/新变更流程处理。状态变化通过条件更新防止并发覆盖。

### 8.2 下游合同状态与金额规则

```text
DRAFT → ACTIVE → COMPLETED → SETTLED
  └──────────────→ TERMINATED
         ACTIVE ─→ TERMINATED
      COMPLETED ─→ TERMINATED
```

- 激活必须填写签订日期，激活后原始合同额锁定。
- 只有 `ACTIVE` / `COMPLETED` 可添加已生效补充协议和新的付款计划；`ACTIVE` / `COMPLETED` / `SETTLED` 可登记付款或退款。`SETTLED` 表示结算已确认，不代表已付清。
- 合同原始金额不能通过通用草稿接口之外的操作直接改写；金额调整采用 `DownstreamContractAdjustment` 追加记录。
- 付款/退款使用同一合同锁和 Serializable 事务做净额核验；并发冲突返回 `409 PAYMENT_CONFLICT`。
- 最终结算单完成外部确认且正式过账后，系统自动将合同状态置为 `SETTLED`；不允许仅通过通用状态接口手动置为已结算。阶段结算只能在 `ACTIVE` / `COMPLETED`，最终结算须先处于 `COMPLETED`，结算调整只允许 `COMPLETED` / `SETTLED`。

### 8.3 CSV 格式

编码建议 UTF-8。列名为：

```csv
code,name,parentId,unit,quantity,unitPrice,totalPrice,sortOrder
```

`parentId` 可引用本次导入文件中已出现的父项编号，也可引用当前项目已存在父项编号或 ID。项目内 `code` 不可重复。当前不支持直接导入 `.xlsx` 文件。

## 11. 备份、恢复及维护

建议每天使用 PostgreSQL 原生工具备份数据库，文件目录由单位备份策略保护。可在 PowerShell 中运行（示例路径需按安装版本调整）：

```powershell
$env:PGPASSWORD = '数据库密码'
& 'C:\Program Files\PostgreSQL\16\bin\pg_dump.exe' -h 127.0.0.1 -U cms_user -Fc -f 'D:\Backups\cost_management.dump' cost_management
Remove-Item Env:PGPASSWORD
```

恢复前先创建空数据库并进行演练：

```powershell
$env:PGPASSWORD = '数据库密码'
& 'C:\Program Files\PostgreSQL\16\bin\pg_restore.exe' -h 127.0.0.1 -U cms_user -d cost_management --clean --if-exists 'D:\Backups\cost_management.dump'
Remove-Item Env:PGPASSWORD
```

生产恢复前应暂停 API 写入、先备份当前库、确认权限并在恢复后检查项目数、合同金额、成本汇总和登录流程。不要把明文密码写入长期脚本或命令历史；示例仅演示参数位置。

| 局域网其他电脑无法访问 | 默认 `HOST=127.0.0.1` 仅允许本机访问；如需内网使用，配置监听地址、防火墙和 HTTPS 反向代理，不要无保护开放端口 |

- `/` 是全局经营总览，只汇总当前账号有权限访问的全部项目；该页面不再查询当前选中项目的成本分析接口。服务端 `/dashboard` 返回全局合计及项目级目标成本、实际成本、回款、成本偏差和回款比例。

- 工作台内通过共享横向页签切换 `/workspace/contracts`、`budget`、`progress-bills`、`changes`、`downstream-contracts`、`downstream-finance`、`costs` 和 `analysis`。每个业务模块仍是独立页面，避免把目标成本树、进度款表单和变更状态流合并成过长的单页。
- 旧 URL（如 `/contracts`、`/budget`、`/changes`）保留路由重定向，兼容历史书签和旧模块内链接。
- 主合同页面默认显示摘要卡、原始/有效合同金额及关键条款；建档或编辑资料时才打开对话框。原始合同金额仍只读锁定。
- `DownstreamContract.status=SETTLED` 的界面名称为“结算已确认”；最终结算正式过账后由系统推进该状态。未付清的应付仍可按已过账应付余额支付，状态本身不表示已付清。



## 14. v1.4.0-rc.1 往来单位主数据与经营档案

### 14.1 核心数据关系

- `BusinessParty` 是统一单位主档，`BusinessPartyRole[]` 允许一个主体同时承担建设单位、材料供应商、劳务/专业分包、设备租赁、服务商或其他角色。`creditCode` 可空且全局唯一；`normalizedName` 建普通索引而不是唯一索引，因为相同显示名称在经管理员确认后允许对应不同法律主体。
- `Project.ownerPartyId`、`DownstreamContract.counterpartyPartyId`、`CostEntry.businessPartyId` 为可空关联字段；现有 `ownerName`、`counterpartyName`、`vendorName` 仍保留作为业务记录的名称快照，不随主档更名批量覆盖。
- `identityVerified` 默认 false。系统管理员只有在记录核验依据后才可将主体标记为已核验。通过旧文本名称回填的档案保留“历史名称回填、待核验”备注，单位经营档案持续显示警告。
- 迁移 `20261014020000_business_party_master` 只追加新表、枚举、关联列、索引和外键；禁止修改既有已交付迁移。上线前应备份 PostgreSQL，先在副本上执行 `prisma migrate deploy` 并核对关联数和孤立关系。

### 14.2 API 与前端

- `GET /api/parties` 支持名称、历史名称、统一社会信用代码及业务角色检索；`POST /api/parties` 创建档案；`PATCH /api/parties/:id` 为管理员专用的主档维护入口；`GET /api/parties/:id` 提供单位经营档案摘要及关联业务数据。
- 创建合同可传 `counterpartyPartyId`/`ownerPartyId` 明确选择主体；只有自由文本名称且匹配唯一现有档案时才复用；出现多个同名主档时应拒绝模糊选择。主合同相对方当前以项目主档的 ownerParty 关联为来源。
- `BusinessPartyPicker` 实现名称/代码搜索与快速建档；`BusinessPartiesPage` 是单位库；`BusinessPartyDetailPage` 是跨项目单位经营档案。单位汇总接口的所有项目型查询均须使用 `projectScope` 权限过滤。
- 公司级主档更新/更名/停用及身份核验由 ADMIN 控制；非管理员可以在其具备业务权限的项目内创建新档案，但不能核验单位身份。银行等敏感资料不得在普通用户列表接口中返回。

### 14.3 数据治理和金额口径

- 同名不同法律主体不得只靠名称拆分；必须由管理员确认并提供独立统一社会信用代码。重复信用代码由数据库唯一约束阻止。
- 历史文本的规范化名称回填是迁移辅助，不能视为法律身份已验证。验收必须抽查回填映射并复核单位警示；不能将待核验的跨项目汇总直接当作财务对账结论。
- 单位页分开展示主合同金额、分供合同金额、已结算金额、应付未付、供应商待返还/抵扣、净付款、核验发票和实际成本。禁止把合同金额当收入实现、把付款当成本或把收入/支出合同简单抵销为利润。
- 独立成本记录可以关联单位；已关联分供合同的成本以合同相对方为权威关联。单位页的独立成本摘要展示全量聚合数，明细列表只展示最新 200 条并有范围提示。

### 9.3 登录凭证安全
