# 开发、部署与维护指南

## 1. 环境要求

- Windows 10/11 或 Windows Server（使用仍在安全维护期内的版本）。
- Node.js `>=24.0.0`。
- PostgreSQL 16+。
- Git 与可用的 npm registry。
- 本项目 Prisma 版本为 7.10.1；保持根锁文件，安装使用 `npm ci`。

## 2. 首次开发环境

在仓库根目录：

```powershell
npm ci
Copy-Item apps/api/.env.example apps/api/.env
```

编辑 `apps/api/.env`，至少提供测试数据库的 `DATABASE_URL`、随机 `JWT_SECRET`（至少 32 字符）和首次种子管理员配置。不要提交 `.env`。先确认连接字符串指向可丢弃的测试库，再执行：

```powershell
npm run db:validate
npm run db:generate
npm run db:deploy
npm run build
npm test
npm run validate:release-candidate
npm run dev
```

根脚本和工作区脚本以 `package.json` 为准。数据库迁移命令会修改目标数据库；不要在生产库试验。

## 3. 常用脚本

| 命令 | 用途 |
|---|---|
| `npm ci` | 根据根锁文件重复安装依赖 |
| `npm run db:validate` | 校验 Prisma schema |
| `npm run db:generate` | 生成 Prisma Client |
| `npm run db:deploy` | 执行已提交迁移（需要正确的数据库连接） |
| `npm run build` | 生成客户端并构建 API/Web |
| `npm test` | API 单元测试 |
| `npm run lint` | API 与 Web 类型/静态检查 |
| `npm run validate:release-candidate` | 发布候选静态/契约检查集合 |
| `npm run dev` | 同时启动 API/Web 开发进程 |
| `npm run worker -w @cms/api` | 独立启动已构建后台 worker |

AI checkpoint 的 schema 初始化为受控的一次性部署步骤，不由普通请求执行 DDL，详情见[AI 助手实施与准入](AI助手实施与准入.md)。

## 4. Windows 原生部署

脚本位于 `scripts/windows/`，当前常用入口：

```powershell
.\scripts\windows\prepare-windows.ps1
.\scripts\windows\start-windows.ps1
.\scripts\windows\stop-windows.ps1
```

首次准备脚本会做运行时检查、依赖安装、构建和按配置迁移/种子处理；脚本参数以当前源码帮助与内容为准。先在隔离环境演练，不要在生产首次部署时盲目执行全流程。

使用服务/计划任务前，确保运行身份有权读取构建目录、`apps/api/.env`、持久化数据目录和日志目录。Windows 上文件权限需要配置 NTFS ACL；不能用 POSIX 文件权限假设替代。凭证附件默认位于 API 的受控目录，应设置独立持久化路径并纳入备份。

## 5. 网络与安全

- 本机默认开发端口为 3001；生产内网/公网地址以实际反向代理配置为准。
- 公网访问必须通过 HTTPS 反向代理，启用 secure cookie 和独立密钥；不要直接暴露未保护的 Node 监听端口。
- 不要提交 `.env`、密钥、备份、真实业务样本或未脱敏日志。
- 初次上线前创建最小权限数据库账号并确认迁移所有权、备份恢复与审计目录权限。
- AI 助手开关默认关闭；不要为“测试能否打开”而在公共部署打开。

## 6. 备份与恢复

发布前验证数据库备份与恢复到独立目标。检查 schema/table 清单、业务数据完整性、登录/项目读取、凭证附件、密钥可用性及实际恢复耗时。记录恢复点与数据损失窗口。CI 的合成数据 pg_dump/pg_restore 演练只证明脚本路径可工作，不证明生产灾备能力。

## 7. 故障排查顺序

1. 核对 Node.js 版本是否为 24+，再运行 `npm ci`。
2. 检查 `apps/api/.env` 是否缺项，数据库是否启动、连接字符串是否指向预期测试库。
3. 运行 `npm run db:validate` 和 `npm run db:generate`；不要手工修改生成客户端。
4. 查看 API 日志时先脱敏，绝不贴出 token、Cookie、连接串、API key 或真实业务数据。
5. 若迁移失败，保留完整日志与迁移状态，优先做经过审查的向前修复或恢复演练，不执行臆测的破坏性回滚 SQL。

## 8. 发布原则

一个工作流通过不等于产品已完成。候选发布必须同时有完整构建/测试结果、真实脱敏预发布数据对账、浏览器关键流程验收、Windows 原生部署演练、可恢复备份和业务负责人签认。当前 RC 状态与未关闭项见[发布与迁移验收](发布与迁移验收.md)。
