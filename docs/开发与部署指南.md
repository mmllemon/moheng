# 开发、部署与维护指南

## 1. 环境要求

- Windows 10/11 或 Windows Server（使用仍在安全维护期内的版本）。
- Node.js `>=24.0.0`（Node.js 24+）。
- Windows 执行 `scripts/windows/*.ps1` 时使用 PowerShell 7+（`pwsh`），避免旧版 Windows PowerShell 5.1 的脚本编码兼容问题。
- PostgreSQL 16+。
- Git 与可用的 npm registry。
- 本项目 Prisma 版本为 7.10.1；保持根锁文件，安装使用 `npm ci`。

## 2. 首次开发环境

在仓库根目录：

```powershell
npm ci
Copy-Item apps/api/.env.example apps/api/.env
```

编辑 `apps/api/.env`，至少提供测试数据库的 `DATABASE_URL`、随机 `JWT_SECRET`（至少 32 字符）和首次种子管理员配置。不要提交 `.env`。先确认连接字符串指向可丢弃的测试库，再执行：

`npm test` 与发布门禁中的报表模板测试会通过 `apps/api/scripts/load-test-database-url.mjs` 仅加载测试所需的 `DATABASE_URL`：优先使用当前 shell 中已设置的值，否则从 `apps/api/.env` 读取该字段；不会把整个 `.env` 的 `NODE_ENV`、JWT 密钥等配置注入测试进程。请先正确配置该文件；`DATABASE_URL` 必须指向隔离测试库，不要将它复制到日志或聊天中。

```powershell
npm run db:validate
npm run db:generate
npm run db:deploy
npm run build
npm test
npm run validate:release-candidate
npm run dev
```

根脚本和工作区脚本以 `package.json` 为准。数据库迁移命令会修改目标数据库；不要在生产库试验。

## 3. 常用脚本

| 命令 | 用途 |
|---|---|
| `npm ci` | 根据根锁文件重复安装依赖 |
| `npm run db:validate` | 校验 Prisma schema |
| `npm run db:generate` | 生成 Prisma Client |
| `npm run db:deploy` | 执行已提交迁移（需要正确的数据库连接） |
| `npm run build` | 生成客户端并构建 API/Web |
| `npm test` | API 单元测试 |
| `npm run lint` | API 与 Web 类型/静态检查 |
| `npm run validate:release-candidate` | 发布候选静态/契约检查集合 |
| `node scripts/validate-ui-polish.mjs` | 75 项 UI 规范/token/文档静态检查 |
| `npm run ui:visual` | 浏览器视觉回归：26 路由横向溢出、大面积圆角、pageerror、焦点/弹窗 |
| `npm run ui:axe` | WCAG 2 A/AA axe：20 个主要页面 |
| `npm run dev` | 同时启动 API/Web 开发进程 |
| `npm run worker -w @cms/api` | 独立启动已构建后台 worker |

AI checkpoint 的 schema 初始化为受控的一次性部署步骤，不由普通请求执行 DDL，详情见[AI 助手实施与准入](AI助手实施与准入.md)。

UI 浏览器门禁需要可登录的本地 API/Web 服务与测试管理员账号；`ui:visual` / `ui:axe` 不替代产品逐页签认。默认查找系统 Chrome，其他 Chromium 路径用 `CHROME_PATH` 指定。截图和本机报告保存在忽略目录，不提交仓库。当前 UI 结果与已知缺口见[UI 验收 Hana](UI-验收-hana.md)。

CSV 报表导出支持受权限约束的台账数据导出；导出前应核对项目范围，下载后按组织的数据保护要求保存，不要把真实财务 CSV 或未脱敏样本提交到代码仓库。

## 4. Windows 原生部署

脚本位于 `scripts/windows/`，当前常用入口：

```powershell
.\scripts\windows\prepare-windows.ps1
.\scripts\windows\start-windows.ps1
.\scripts\windows\stop-windows.ps1
```

首次准备脚本会做运行时检查、依赖安装、构建和按配置迁移/种子处理；脚本参数以当前源码帮助与内容为准。先在隔离环境演练，不要在生产首次部署时盲目执行全流程。

使用服务/计划任务前，确保运行身份有权读取构建目录、`apps/api/.env`、持久化数据目录和日志目录。Windows 上文件权限需要配置 NTFS ACL；不能用 POSIX 文件权限假设替代。凭证附件默认位于 API 的受控目录，应设置独立持久化路径并纳入备份。

## 5. 网络与安全

- 本机默认开发端口为 3001；生产内网/公网地址以实际反向代理配置为准。
- 公网访问必须通过 HTTPS 反向代理，启用 secure cookie 和独立密钥；不要直接暴露未保护的 Node 监听端口。
- 不要提交 `.env`、密钥、备份、真实业务样本或未脱敏日志。
- 初次上线前创建最小权限数据库账号并确认迁移所有权、备份恢复与审计目录权限。
- AI 助手开关默认关闭；不要为“测试能否打开”而在公共部署打开。

## 6. 备份与恢复

发布前验证数据库备份与恢复到独立目标。检查 schema/table 清单、业务数据完整性、登录/项目读取、凭证附件、密钥可用性及实际恢复耗时。记录恢复点与数据损失窗口。CI 的合成数据 pg_dump/pg_restore 演练只证明脚本路径可工作，不证明生产灾备能力。

## 7. 故障排查顺序

1. 核对 Node.js 版本是否为 24+，再运行 `npm ci`。
2. 检查 `apps/api/.env` 是否缺项，数据库是否启动、连接字符串是否指向预期测试库。
3. 运行 `npm run db:validate` 和 `npm run db:generate`；不要手工修改生成客户端。
4. 查看 API 日志时先脱敏，绝不贴出 token、Cookie、连接串、API key 或真实业务数据。
5. 若迁移失败，保留完整日志与迁移状态，优先做经过审查的向前修复或恢复演练，不执行臆测的破坏性回滚 SQL。

## 8. 公网配置与回滚

公网访问需配置 `PUBLIC_BASE_URL`、`COOKIE_SECURE=true`、受信代理和与 JWT 不同的 `MFA_ENCRYPTION_KEY`、`LOGIN_ATTEMPT_HMAC_KEY`；集成凭据与备份也使用独立密钥策略。上线前先在隔离环境验证反向代理、MFA、会话撤销和备份恢复。若迁移/部署失败，保留日志和迁移状态，采用经过审查的向前修复或已演练的恢复方案；不要臆测执行破坏性回滚 SQL。

## 9. 分阶段验证原则

一个工作流通过不等于产品整体已完成。**开发阶段**优先把源码、单测、隔离 PostgreSQL 集成测试、权限/金额边界和真实浏览器交互逐项闭环；每次都以最新代码和实际运行证据更新状态。

**预投产/投产阶段**才在条件具备后开展真实历史数据迁移核对、Windows 目标环境安装与 ACL 检查、数据库与附件联合恢复，以及业务/财务/审计签认。当前开发阶段不要求提供不存在的生产历史台账或正式签认材料；CI 合成夹具也不能冒充真实历史数据。

当前开发功能状态见[产品范围与当前状态](产品范围与当前状态.md)和[后续四阶段开发路线图](后续四阶段开发路线图.md)；CI 证据与后续投产门禁见[开发阶段验证与后续投产门禁](发布与迁移验收.md)。


## 10. Git 分支与 PR 协作规则

仓库使用轻量的 PR 工作流，目标是保持 `main` 可集成、避免旧分支无限累积。

### 分支约定

- **`main` 是唯一长期集成分支。** 新开发从最新的 `main` 创建短期分支；不要把个人开发分支当作长期主线。
- 按工作内容使用清晰前缀：`feat/`（功能）、`fix/`（缺陷）、`docs/`（文档）、`chore/`（维护）。分支名应能对应一项明确工作。
- 一个分支尽量只承载一个可审查的变更集。涉及功能代码、数据库迁移、测试或必要文档时，应在同一 PR 内保持相互一致。
- 日常变更通过 PR 合入 `main`。合并前检查 PR 描述、实际 diff、目标分支，以及**当前最新头提交**对应的必需 CI；旧提交上的绿灯不能代表新提交已通过。
- 优先使用 Squash merge 保持 `main` 历史易读；如某项工作确实需要保留多提交历史，再按实际需要选择合并方式。

### 合并后自动删除

GitHub 仓库已开启 **Automatically delete head branches**（仓库设置中的 `delete_branch_on_merge=true`）。正常情况下，PR 合并后 GitHub 会删除该 PR 的远程源分支；`main` 不受影响。

这一设置**不追溯清理启用前已经存在的旧分支**，因此仍可能在分支页面看到早期已合并 PR 的源分支。遇到这种情况：

1. 打开分支对应的 PR，确认 PR 的目标是 `main` 且状态为已合并。
2. 确认当前需要保留的改动已进入 `main`。若分支没有对应 PR，不要只凭分支名或“落后于 main”的提示判断；应检查它相对 `main` 的实际文件差异以及是否存在未合入的工作。
3. 只有确认无需保留后，才删除旧远程分支。删除分支引用不会撤销已经合入 `main` 的提交；但若仍有未合入工作，该工作将失去该远程分支入口，因此不应批量盲删。

清理后可在 [GitHub Branches 页面](https://github.com/mmllemon/moheng/branches)复查。正常维护目标是只保留 `main` 和当前确实有在途工作、且尚未合并的短期分支。不要为了凑成“只剩一个分支”而删除仍承载未合入工作的分支。
