# 墨衡框架演进方案 v2.2.0-rc.1

- 日期：2026-10-15
- 基线：`v2.1.0-rc.1`
- 目标候选：`v2.2.0-rc.1`
- 定位：技术架构增量演进，不等于生产验收或发布签字

## 1. 目标与决策

目标是在不牺牲合同、结算、应收应付、退款冲销及审计规则的前提下，提升模块可替换性、外部集成能力、可诊断性和升级可控性，同时维持低部署负担。

**架构决策：继续使用模块化单体（Modular Monolith），以标准 REST API/OpenAPI 为集成边界，以 PostgreSQL 为业务事实源，按需引入可选适配器。**

当前不迁移到 Frappe/ERPNext，也不拆微服务；不增加必需的 Redis、RabbitMQ、Kafka、独立对象存储或 Kubernetes。除非实际规模、部署频率、隔离需求或可靠性数据证明有必要，否则先在同一进程、同一部署包和单个 PostgreSQL 数据库中完成模块化。

## 2. 目标架构

```text
浏览器 / 未来移动端 / 外部系统
             │ HTTPS + REST + OpenAPI
             ▼
     Fastify 单体应用（同源静态前端）
     ├── 身份认证、会话与权限
     ├── 项目、主合同、分供合同
     ├── 业主结算 / 应收 / 收退款
     ├── 分供结算 / 应付 / 付款退款
     ├── 预算、实际成本、成本分析
     ├── 往来单位主数据
     ├── 审计、报表、模板、待办预警
     └── 模块注册表 + API 元信息目录
             │ 应用服务 / 领域规则 / 数据访问
             ▼
          Prisma ORM
             ▼
       PostgreSQL（业务事实源）

      可选的外部集成适配器（按需启用）
      ├── 企业微信 / 邮件 / 短信
      ├── 电子签章 / 合同平台
      ├── 财务 / ERP / 发票平台
      ├── S3 兼容存储 / OSS
      └── AI 服务 / 其他内网 API
```

图中的层次是逻辑边界，不是独立服务。v2.2 先把路由挂载注册集中化；后续只对新增或被修改的业务逐步抽取应用服务、领域规则和适配器，不要求一次性重写旧模块。

## 3. 当前候选已落实的源码改动

### 3.1 集中 API 模块注册

新增 `apps/api/src/platform/module-registry.ts`，统一声明现有路由插件、挂载前缀、模块 ID、中文名称和用途。`server.ts` 调用统一注册入口，不再维护第二套散落的路由注册清单。

这带来三个收益：路由发现与模块清单同源；可由 `/api/meta` 暴露集成目录；后续新增模块可通过同一入口接入。它**不是**动态加载任意第三方插件的开放执行器，也没有赋予模块绕过认证、项目权限或领域规则的能力。

### 3.2 元信息与探针

| 路径 | 语义 | 用途 |
|---|---|---|
| `GET /api/meta` | 版本、API 主版本、基础路径、模块目录、兼容策略 | 集成前能力发现；返回目录不等同于授权结果 |
| `GET /health/live` | 仅确认 API 进程在运行 | 进程存活探测；数据库故障不应让它误判进程已死 |
| `GET /health/ready` | 检查数据库是否可访问 | 部署/监控就绪探测；数据库不可用返回 503 |
| `GET /health` | 与旧部署脚本兼容的就绪探针别名 | 平滑迁移，当前不删除 |
| `/docs/` | Fastify Swagger UI | 读取实际 API schema 与接口定义 |

`/api/meta` 里的模块 `mountPrefix` 是路由插件的挂载前缀，**不是**该模块全部端点的清单。真实路径、方法、参数和响应以 `/docs/` 的 OpenAPI schema 为准。

### 3.3 请求追踪与日志保护

- 响应附加 `x-request-id`，用于将客户端反馈与服务端日志关联。
- 服务端错误日志附带同一请求 ID。
- Pino 日志对 Authorization、Cookie、Set-Cookie、密码、刷新令牌和 API Secret 等常见字段配置脱敏。
- 生产环境在没有显式 `CORS_ORIGIN` 时不再默认允许开发用 `http://localhost:5173`；开发环境仍保留 Vite 本地来源默认值。跨域部署应明确配置允许来源，而非通过通配符扩大信任面。

这些措施是基础设施保护层，不替代密码安全、HTTPS、接口限流、项目级授权和对每个资源的服务端检查。

### 3.4 兼容性与变更边界

- 继续使用既有 `/api` 路径，不借本轮更改财务接口的 URL 或 JSON 结构。
- 目前所有 API 标注为 `apiMajorVersion: 1`。破坏性接口变更必须走单独的 API 主版本路径（例如 `/api/v2`），不能悄悄改变现有金额语义。
- 本轮不修改 Prisma Schema、不新增迁移、不改写合同金额生效、结算过账、应收应付和退款冲销规则。
- 不新增运行时服务依赖；Windows 原生单机部署形态保持不变。

## 4. 模块化边界规则

新功能和后续重构按以下规则逐步执行：

1. **路由层只负责 HTTP 适配。** 做参数解析、调用用例、映射状态码和响应，不在路由中堆叠复杂的财务推导。
2. **应用服务负责用例编排。** 比如“确认外部变更”“过账最终结算”“退款反向核销”都应显式表达流程边界、权限与事务要求。
3. **领域规则负责金额与状态合法性。** 有效合同额、累计结算差额、应收/应付余额、退款冲销、预付款与质保金等规则必须集中并保留回归测试，不能因接入外部服务而重复实现。
4. **适配器包住外部差异。** 文件存储、通知、电子签章、财务系统和 AI 调用使用窄接口隔离厂商 SDK、凭证及重试策略。
5. **数据访问以 PostgreSQL 为事实源。** 缓存只能是可重建副本；不能让缓存成为金额真值。跨模块写入使用数据库事务，审计记录应与需要审计的业务提交保持一致。
6. **按需抽取目录，不进行形式主义迁移。** 新/改模块可逐步采用 `src/modules/<module>/{routes,application,domain,infrastructure}` 结构；旧代码在触碰时再移动，禁止只改目录就宣称完成架构升级。
7. **模块间通过公开服务/领域接口协作。** 避免新模块直接写入其他模块的表或复制业务规则。必要的跨域写入应由明确的应用服务统一编排。

## 5. 对外 API 与服务接入约定

### 5.1 API 契约

- OpenAPI 是对外接口的可读契约；新增、修改接口应同步 schema、文档、访问范围和自动化测试。
- 兼容性优先：新增字段尽量可选；不移除或重新解释已有字段；破坏性变化单独发版。
- 响应沿用项目既有成功/失败结构；错误必须给稳定的错误码，不能只依赖中文报错文本。分页、排序和过滤需明确定义上限与默认值。
- `/api/meta` 仅用于版本和能力发现；不能作为身份验证或授权判断依据。实际权限以每次 API 调用时的服务端授权为准。
- 所有涉及项目的查询都必须重新检查当前用户项目成员关系。不能因为外部集成账号、前端隐藏菜单或调用方提供 `project_id` 就跳过授权。

### 5.2 认证、幂等和可靠性

- 人员登录继续沿用既有会话机制；外部系统接入另设服务账号或客户端凭据，不共享个人账号。
- 外部服务账号实行最小权限、可撤销、可轮换密钥和可审计；禁止将凭据写进代码、模板或业务日志。
- 写入合同、结算、支付、退款、到账等不可轻易重试的流程时，外部集成需设计业务幂等键、重复请求检测、并发限制和结果查询；同一幂等键不能重复记账。
- 异步通知需要重试时，先定义 delivery ID、幂等、失败/死信观察、重放权限和审计。只有当“数据库提交与外部事件发送不能丢失”的场景实际启用后，再增加 PostgreSQL outbox；初期不先上消息中间件。
- Webhook 接收端应验证签名、时间戳和重放保护，设置请求体与频率上限，并记录可追踪的处理结果。

### 5.3 建议的适配器接口

根据首个真实需求实现对应接口，而不是一次性创造一套空泛插件体系：

- `FileStorageAdapter`：本地受控目录、S3 兼容服务或云对象存储间切换。
- `NotificationAdapter`：站内事件、企业微信、邮件等通知通道。
- `SignatureAdapter`：不同电子签章平台的签署发起、查询和回调验签。
- `FinanceAdapter`：财务/ERP 的科目、凭证或付款数据交换。
- `InvoiceAdapter`：电子发票平台的检索、校验与状态同步。
- `AIProviderAdapter`：模型供应商可切换，但提示词、权限和审计不能移交给模型决定。

适配器只提供技术能力。供应商确认、外部业主确认、内部审批、金额生效和记账时点始终由本系统业务规则确定。

## 6. 部署与运维建议

### 默认部署

- Windows 原生：一个 Node.js API/Web 进程 + PostgreSQL Windows 服务；前后端同源，运维入口较少。
- Docker Compose：作为可选方案，用于开发、测试或已具备容器运维能力的环境；不把 Docker Desktop 设为终端用户前提。
- 继续不要求 Redis、Kafka、RabbitMQ、Kubernetes 或独立网关。外部反向代理只在内网/公网 HTTPS、公司统一入口等场景需要时启用。
- 本地受控文件目录可作为小规模部署的当前存储方式；以后通过 `FileStorageAdapter` 接 S3 兼容存储/OSS。迁移时要保持稳定文件 ID、权限检查、元数据与备份恢复规则。

### 监控与恢复

- 负载均衡、进程管理或 Windows 任务计划程序用 `/health/live` 判断进程存活，用 `/health/ready` 判断数据库依赖是否可用。
- 以 `x-request-id` 关联用户报错、API 日志和外部集成追踪；生产日志不记录访问令牌、密码、敏感文件内容或完整财务凭证。
- 数据库备份必须定期执行恢复演练，不能仅确认备份文件存在。部署升级前备份数据库和受控文件目录；迁移脚本只采用追加式变更，先在数据库副本验证。
- 设置并记录依赖版本矩阵、锁文件、运行时版本和迁移版本；生产安装采用 `npm ci`，避免无锁依赖漂移。

## 7. 技术追新策略（截至 2026-10-15）

原则是“**及时吸收有价值的稳定能力，不追逐版本数字**”。当前代码的框架版本和未来候选不能混写：只有锁定依赖、完成测试与部署演练的版本才算已升级。

## 8. 实施路线与 Gate

### Gate A：本候选架构契约（v2.2）

- 所有 API 路由插件统一经注册表挂载；新增模块有唯一 ID、用途说明和挂载前缀。
- `/api/meta`、`/health/live`、`/health/ready` 行为符合文档，`/health` 保持兼容。
- 生产默认 CORS 不包含开发端口；日志脱敏和 `x-request-id` 检查通过。
- 财务领域规则、已发布迁移、原有 API 路径不因本次架构调整而变更。
- 静态契约检查全部通过。

### Gate B：发布基础能力（必须完成后才能退出 RC）

- 在联网且可安装依赖的 Windows/CI 环境准备规定的 Node.js 24 LTS 与 PostgreSQL。
- 生成、人工复核并提交 `package-lock.json`；清洁环境运行 `npm ci`。
- 运行完整 TypeScript 检查、lint、API 测试、前后端生产构建、Prisma validate/generate。
- 在数据库备份副本执行所有追加式迁移，确认历史迁移校验和、历史业务记录、有效合同额、应收应付与退款余额。
- 在真实 PostgreSQL 下测试项目越权、事务回滚、金额并发更新、审计原子性、幂等与 XLSX 导入导出。
- 执行 Windows 原生安装、启动/停止、重启、备份恢复以及 Edge/Chrome 实际流程；报表用 Excel/WPS 验证打开、格式和打印。

### Gate C：可集成契约（后续 v2.3）

- 从 OpenAPI 生成或至少自动验证对外客户端类型；检查响应 schema、错误码、分页上限和 API 兼容变化。
- 每个资源端点测试：匿名、无项目成员、只读成员、可编辑成员、管理员五种授权行为。
- 针对外部写入增加幂等、并发和重复回调测试。所有外部集成凭证可轮换/撤销，所有调用可按请求 ID 追踪。

### Gate D：可选外部连接器（按真实业务启用）

逐个连接器定义范围、凭证配置、字段映射、超时、重试、幂等、失败告警和回滚；连接器关闭时核心系统照常运行。仅当外部事件必须持久可靠交付时增加 PostgreSQL outbox；只有遇到已证明的吞吐、独立扩缩容或部署隔离需求时再考虑独立 Worker/服务。

## 9. 明确暂不做的事情

- 不因追求“自由度”而引入可执行任意代码的插件市场。
- 不在目前规模预建微服务、事件总线、Kubernetes、服务网格或分布式事务。
- 不为了跟上最新版而同时升级 React、Vite、Prisma、Node.js 和 PostgreSQL。
- 不让 AI/外部平台直接更改业务状态或金额；AI 只能经权限受控的 API 作为辅助能力。
- 不把静态源码 marker 检查等同于真实构建、数据库集成测试或生产验收。

## 10. 发布结论

v2.2.0-rc.1 已落实 API 模块注册、模块目录发现、健康探针、请求追踪、日志脱敏和生产 CORS 默认保护，并通过静态候选契约检查。但受限于当前运行环境与缺失的可复现依赖安装，尚不能据此声称严格类型检查、真实 PostgreSQL、浏览器 E2E 或 Windows 发布门禁已通过。完成 Gate B 前保持 `rc` 状态。
