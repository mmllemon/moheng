# 产品范围与当前状态

最后校准：2026-11-05。本文按主分支 `4d54e81` 更新；版本、功能集成和验收证据分别记录，不能将历史 RC/CI 文档里的状态直接当作当前 HEAD 状态。

## 产品定位

墨衡服务施工单位项目经济成本与经营台账，核心使用者是造价/成本人员与管理人员。权限以公司、项目和角色为边界。当前技术架构是模块化单体：共享业务对象、PostgreSQL、权限/流程/审计体系；不因增加报表或 AI 提前拆分微服务。

## 当前主干已具备的业务域

- **项目与主合同：** 项目档案、项目上下文、主合同、原合同基线与当前有效合同额。
- **目标成本与实际成本：** 清单层级、目标成本、成本记录，以及成本与项目/分供合同的关联。
- **变更签证：** 公司内部流程与业主/授权代表外部确认分离；凭证、金额差异与关键状态有审计路径；提交人不得审批本人提交的业务。
- **业主侧财务：** 进度款、最终结算、应收、收款/退款分配、预付款和质保金。最终结算按最终累计确认额减既有已过账累计额计算差额；允许合法负向差额，负/零差额不允许继续填写普通扣款。
- **分供侧财务：** 分供合同与调整、结算、应付、付款/退款核销、预付款、质保金、发票核验；应付、现金支付与实际成本分别记录，不得互相替代。
- **往来单位：** 统一主数据、身份核验标记、跨项目经营档案和关联记录。仅凭名称匹配到未核验档案不会自动关联；主合同/分供合同 API 返回明确冲突，要求核验或显式选择档案。
- **系统管理与安全：** 用户和项目成员权限、安全事件、关键动作审计、系统参数/字典、授权治理与 PostgreSQL 后台任务。
- **报表中心：** 标准 CSV/XLSX 与报表工作室；项目级、公司级、往来单位级数据源、字段/单元格绑定、重复区域和样式。PR #4 已将产品完善工作合入主干，PR #6 修复报表打印；两种 XLSX 导出路径均含样式化总览页，并对数据范围、工作表、截断和限制给出说明。复杂模板的真实浏览器视觉与打印验收仍需继续。
- **AI 助手：** LangGraph + PostgreSQL checkpoint、会话/消息、持久化运行事件与 SSE 回放、取消/重试/幂等、上下文预算、模型调用边界、每用户活动任务与提交频率限制、供应商 token 用量记录和项目范围近 30 天用量摘要。工具限定为项目经营概览、成本偏差与变更资料完整性三个只读业务工具。助手已改为标题栏入口打开的全局三栏弹窗，旧 `/cost/assistant` / `/assistant` 只作为兼容入口。
- **界面与交互：** Hana 1.1.35 的纸面/外壳/设置工作区、三级交互半径与状态 token 已全仓落地；项目驾驶舱、主合同、待办、报表、变更、账号页完成结构重排；全局命令中心和助手弹窗使用同一套焦点、hover、selected 与 16px 卡片 inset 规则。
- **2026-11-04 起的收口（`4d54e81` 基线）：** 全站卡片统一为台账三件套 `ldg-section` / `ldg-section-head` / `ldg-section-card`（业务页 12 页、设置窗 12 页、报表中心/设计器/预览、成本分析），`.panel` 只剩报表工作室外壳且按约定不向内动；运行时量卡头的 `useDetachedPanelHeaders` 机制退役；助手弹窗改为 `createPortal` 挂 body，修掉窄屏下页面操作按钮盖住关闭键；金额上限分两档、前端改按分比较；三条 PostgreSQL 路由级回归接入 CI。
- **打印与 PDF 分页（阶段一验收完成）：** 预览页原先打印出来是白纸（`@layer legacy` 里的全局 `visibility: hidden` 从未被无层的 `hana.css` 推翻）；现已把打印样式集中到 `hana.css` 分三组（通用外壳、预览页纸张、设计器纸张），并修掉外壳 100vh 内部滚动导致第 2 页起不参与分页、`mask-image` 合成层导致表头不重复与行被切断两个问题。真 PDF 回看：预览 17 行 2 页、注入 221 行 23 页且第 2/5 页有重复表头、8 张标准台账 1 至 2 页、设计器直印与完整报表各 1 页、工作室 A3 纵向真模板 6 页且第 2 页起重复 3 行表头。

上述是源码能力盘点，不表示每个页面均已完成浏览器验收、真实模型 E2E 或用户体验确认。

## 当前仍需继续的开发工作

1. **经营链路集成回归：** 业主最终结算负差额、到账核销、分供付款与分供结算→应付→核销四条链路已有路由级 PostgreSQL 回归（`test:owner-settlement-posting:postgres`、`test:owner-receipt:postgres`、`test:downstream-payment:postgres`、`test:downstream-settlement:postgres`，CI 见 `source-gates.yml` 的 db-integration）。到账核销覆盖部分到账、补齐后转 RECEIVED、超额到账拒绝且不留分配行、负向应收不得登记普通到账、期次超额拒绝、部分退款冲回与超额退款拒绝、以及两笔并发到账合计超额时只允许一笔成功且状态与净核销额一致。分供付款覆盖草稿阶段拒付、同凭证号重复入账拒绝、累计净付款超合同额拒绝且不留半条付款、退款冲减净额与超额退款拒绝、审计里 PAYMENT_RECORDED / PAYMENT_REFUND_RECORDED 与付款行数一致、两笔各 60 万并发抢 100 万额度只成功一笔、以及 ACTIVE 直跳 SETTLED 被状态机拦住而 COMPLETED 跳 SETTLED 需要已过账的最终结算。分供结算覆盖提交人不得自批、未确认不过账、过账生成应付与质保金留置、扣款超额拒绝且不留应付、已有应付时付款必须核销、核销超额与应付已结清拒绝、最终结算把合同推到 SETTLED、“结算确认不等于已付清”仍然要求核销，以及质保金释放（未过账最终结算不得释放、释放生成带分期的应付、分期必须选期次、进度款不得核销质保金应付、释放超额拒绝）与供应商发票核销（未核验不得核销、发票与应付两侧超额均拒绝、汇总口径一致）。质保金没收与应付分期重排也已覆盖：没收不生成应付、重排后合计必须等于净额、发生付款后锁定。仍未覆盖：质保金专项扣回的业务口径、前端在这些错误码上的提示文案。

## 后续投产阶段事项（当前开发非阻塞）

本项目当前按开发状态推进；没有需要本轮核对的生产历史台账，也没有要求本轮取得正式人员签认。只有在准备接入真实历史数据或部署到目标环境后，才安排数据迁移对账、Windows 最小权限 ACL、数据库与附件联合恢复、生产 RPO/RTO、正式业务/财务/审计签认。CI 的隔离 PostgreSQL 和合成夹具是自动化开发证据，不能替代这些未来环境验收；同样不能反过来要求开发阶段凭空提供历史数据或签认。

## 分支与文档纪律

`main` 是唯一长期集成分支；短期开发分支通过 PR 合并。GitHub 合并后自动删除源分支的设置已启用，但不会追溯删除旧分支。分支操作规则见[开发、部署与维护指南](开发与部署指南.md#10-git-分支与-pr-协作规则)。历史记录保留原来的时间与基线，当前状态只在本文、README、更新日志、路线图与发布/投产门禁说明中维护，避免重复且冲突的“当前状态”文本。
