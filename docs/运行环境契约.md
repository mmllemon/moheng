# 运行环境契约

> 目的：把「服务进程以何种形态运行」从散落的 `process.env` 读取，收敛为一处声明 + 明确校验。
> 建立日期：2026-10-23。这是桌面端开工前的硬前提。

## 1. 为什么需要这一层

原先 `apps/api/src/server.ts` 把运行形态写死在代码里：

```ts
PORT: z.coerce.number().int().positive().default(3001),   // 只能显式端口
HOST: z.string().default('127.0.0.1'),
DATABASE_URL: z.string().min(1),                          // 不校验 scheme
```

桌面端（Electron）需要两个和上面直接冲突的东西：

1. **随机端口** — 不能和用户机器上任何软件抢 3001
2. **嵌入式数据库** — 用户机器上没有 PostgreSQL

如果继续让桌面端自己读 `process.env`，它会长出第二套硬编码，web 与 desktop 从此分叉。
所以先立契约。

## 2. 两种运行形态

| | `standalone`（默认） | `embedded` |
| --- | --- | --- |
| 用途 | 独立部署（当前 web 形态） | 嵌入宿主进程（Electron 桌面端） |
| `PORT` | 必须 > 0，**`0` 会被拒绝** | 允许 `0`（系统分配） |
| 数据库 scheme | 只接受 `postgresql://` `postgres://` | 同上，另预留 `pglite:` |
| 拒绝 `pglite` 的理由 | 嵌入式库无法被外部 DBA 接管，不符合备份与审计前提 | 适配器尚未实现，明确拒绝 |
| 就绪握手 | 不写文件 | 可写 `MOHENG_READY_FILE` |

### 为什么 standalone 拒绝 `PORT=0`

`PORT=0` 让操作系统分配端口，这对桌面端是标准做法（避免冲突），
对独立部署却是危险的：运维看不到预期端口，反向代理和监控无从配置。

所以这条限制是**按形态分别施加**的，不是一刀切。

### 为什么 standalone 拒绝 `pglite`

`pglite` 是嵌入式库，没有独立进程、没有远程连接、不能被 pgAdmin 这类工具接管。
独立部署的核心前提之一是「数据库可被 DBA 接管、可独立备份、可做恢复演练」——
引入 `pglite` 会让这个前提失效。这不是技术限制，是部署语义限制。

## 3. 就绪握手

问题：`PORT=0` 之后，桌面端怎么知道 API 真的在哪个端口？

**不能靠读启动日志里的字符串** —— 那是约定，不是协议。日志格式一改就断。

做法是写一个 JSON 文件：

```jsonc
// MOHENG_READY_FILE 指向的文件内容
{
  "host": "127.0.0.1",
  "port": 57524,
  "baseUrl": "http://127.0.0.1:57524",
  "mode": "embedded",
  "databaseScheme": "postgresql",
  "version": "2.19.0-rc.2",
  "publicMode": false
}
```

端口来自 `app.listen()` 的**返回值**，不是自己算的：

```ts
const listenAddress = await app.listen({ port: env.PORT, host: env.HOST });
const parsedAddress = new URL(listenAddress);   // Fastify 返回 http://127.0.0.1:57524
const actualPort = Number(parsedAddress.port);
```

就绪文件里**不含任何数据库凭据**，可安全被 renderer 侧读取。

独立部署不设 `MOHENG_READY_FILE`，行为与改造前完全一致。

## 7. 尚未完成：数据层适配器

`embedded` + `pglite:` 现在会被**明确拒绝**，这是故意的。

理由：如果让它「暂时降级成 postgresql」，嵌入式形态会假成功 ——
用户在桌面端看到程序起来了，实际连的是一个不存在的本地 Postgres，
报错会晚几十秒出现在完全无关的地方。

正确顺序是：

1. 先完成 PGlite 可行性验证（21 个迁移能否原样跑、`pg_advisory_xact_lock` 语义是否仍成立）
2. 适配器接好后，把 `pglite` 加进 `IMPLEMENTED_DB_SCHEMES`
3. 届时 `validateDatabaseForMode` 自动放行，无需改动调用方

这一步在 `validateDatabaseForMode` 里已经有明确落点，改一行常量即可。

## 8. 与桌面端的分工

契约定了，桌面端（`desktop/`）需要做的就明确了：

```js
// 主进程伪代码
const readyFile = path.join(app.getPath('userData'), 'api-ready.json');
fs.rmSync(readyFile, { force: true });            // 先清掉上次的

const api = spawn(nodeBinary, [apiEntry], {
  env: {
    RUNTIME_MODE: 'embedded',
    PORT: '0',                                     // 系统分配
    MOHENG_READY_FILE: readyFile,
    // DATABASE_URL 暂时仍是 postgresql://（PGlite 未接好）
  },
});

const ready = await waitForJson(readyFile);        // 协议，不是约定
win.loadURL(ready.baseUrl);
```

关键点：**`ready.baseUrl` 是唯一可信来源**，不要在桌面端自己拼 `http://127.0.0.1:3001`。

## 9. 一个待决问题

Electron 里 renderer 的 origin 会是 `http://127.0.0.1:<随机端口>`，
而 `CORS_ORIGIN` 在 production 下默认是空字符串（同源模式）。

若 API 本身托管 `dist`（当前已支持，见 `WEB_DIST_DIR`），renderer 与 API 同源，
CORS 不是问题。**建议桌面端走同源托管**，而不是 vite dev server 跨源。

这条无需改契约，但在搭 `desktop/` 时必须确定，否则登录会被 CORS 挡住。
